# Перенос системы на другой курс

Документ для преподавателей других предметов. Отвечает на три вопроса: что
эта система делает, из чего состоит и что придётся переписать под свой курс.

Инструкция по развёртыванию — `admin/SETUP.md`.

---

## 1. Что это

Автоматизация проверки лабораторных работ на GitHub. Решает две задачи:

1. **Организационную** — у каждого студента свой приватный репозиторий,
   студенты не видят работы друг друга.
2. **Рутинную** — при открытии Pull Request бот публикует предварительное
   ИИ-ревью: сверяет работу с требованиями конкретной лабораторной, запускает
   структурные проверки, при возможности собирает и запускает код.

**Чего система не делает:** не ставит оценки и не принимает работы. Это
осознанное ограничение — в промпт агента вшит запрет на формулировки вроде
«работа принята», а сам агент запущен в режиме только для чтения.

### Честно о применимости

Система хорошо работает там, где:

- работа студента — это **код в репозитории** (не отчёт в Word, не расчёт в Excel);
- есть **чёткие формальные требования** к каждой работе, которые можно описать текстом;
- полезно **раннее замечание** до проверки преподавателем.

Плохо подходит, если работы сдаются вне git, если критерий проверки —
исключительно устная защита, или если группа очень большая (упрётесь в
бесплатные квоты, см. раздел 6).

### Стоимость

Ноль при соблюдении лимитов: бесплатный tier Google AI Studio + бесплатные
минуты GitHub Actions. Подробности и расчёт — `SETUP.md`, раздел 12.

## 2. Архитектура

```
.github/
├── workflows/
│   ├── ai-review.yml          # ИИ-ревью PR
│   └── guard-main.yml         # детект push в main в обход PR
└── review/
    ├── config.env             # ← НАЗВАНИЕ КУРСА, модель, лимиты
    ├── common-footer.md       # общие правила ревью
    ├── lib/                   # движок (предметно-независим)
    │   ├── detect-task.sh     #   номер работы из имени ветки
    │   ├── rate-limit.sh      #   лимиты запусков
    │   ├── diff-guard.sh      #   лимит размера diff
    │   └── build-prompt.sh    #   сборка промпта
    └── tasks/                 # ← ВАШ ПРЕДМЕТ
        ├── task1/
        │   ├── prompt.md      #   что проверять в работе №1
        │   └── check.sh       #   структурная проверка (опционально)
        ├── task2/ ... task5/
        └── default/           #   если номер не распознан

admin/
├── manage.sh                  # управление репозиториями (универсален)
├── SETUP.md                   # развёртывание
├── STUDENT_GUIDE.md           # какие документы уходят студенту
├── template-README.md         # ← README шаблона: заготовка для студента
├── template-TASK.md           # ← требования практикума
├── template-GUIDE.md          # ← правила работы (ветки, PR, ревью)
└── .env.example
```

Три файла `template-*.md` копируются в шаблон под именами `README.md`,
`TASK.md` и `GUIDE.md` — это всё, что студент видит помимо `.github/`.

### Как это работает

1. Студент создаёт ветку `task<номер>` и открывает PR в `main`.
2. `detect-task.sh` достаёт номер работы из имени ветки.
3. `rate-limit.sh` и `diff-guard.sh` проверяют, не пора ли пропустить ревью.
4. `build-prompt.sh` собирает промпт: `tasks/task<N>/prompt.md` + вывод
   `check.sh` + diff PR + `common-footer.md`.
5. Агент читает код (без права что-либо менять) и возвращает текст ревью.
6. Workflow публикует его комментарием в PR.

## 3. Что менять под свой предмет

Хорошая новость: **движок предметно-независим**. Меняются в основном тексты.

| Что | Файл | Объём работы |
|---|---|---|
| Название курса | `config.env` → `COURSE_NAME` | 1 строка |
| Файлы с требованиями | `config.env` → `COURSE_DOCS` | 1 строка |
| Промпты по работам | `tasks/task*/prompt.md` | **основная работа** |
| Структурные проверки | `tasks/task*/check.sh` | опционально |
| Требования практикума | `template-TASK.md` | переписать под предмет |
| Правила работы | `template-GUIDE.md` | правки структуры репозитория |
| Заготовка README студента | `template-README.md` | правки под предмет |
| Количество работ | папки `tasks/taskN/` | добавить/удалить |

**Не требуют изменений:** оба workflow, всё в `lib/`, `manage.sh`,
механика лимитов и защиты.

### 3.1. Минимальный вариант (полчаса)

Заработает уже на этом:

```bash
# 1. Название курса
vim .github/review/config.env
#    COURSE_NAME="Базы данных"
#    COURSE_DOCS="README.md"

# 2. Оставить одну папку задания
cd .github/review/tasks
rm -rf task2 task3 task4 task5
vim task1/prompt.md
```

> `config.env` читается через `source`. Пишите значения в двойных кавычках,
> без обратных кавычек и `$(...)` — иначе будут выполнены как команда.
> Скрипт подстановки на всякий случай вычищает такие символы.

### 3.2. Промпт задания

Формат простой — markdown с плейсхолдером `{{WORK_DIR}}` (заменяется на
директорию работы). Пример для курса по базам данных:

```markdown
## Задание: Лабораторная работа №1 — проектирование схемы БД

Требуется: ER-модель предметной области и DDL-скрипт создания схемы
в третьей нормальной форме.

Проверь:

1. В `{{WORK_DIR}}` есть DDL-скрипт (`*.sql`) и описание ER-модели.
2. Все таблицы имеют первичный ключ; внешние ключи объявлены явно
   через `FOREIGN KEY`, а не подразумеваются по именам колонок.
3. Схема в 3НФ: нет повторяющихся групп, нет транзитивных зависимостей
   от неключевых атрибутов. Если нормализация намеренно нарушена —
   в README должно быть обоснование.
4. Типы данных адекватны: не `VARCHAR(255)` под всё подряд, для денег
   не `FLOAT`, даты — датными типами.
5. Индексы: есть ли они под заявленные в задании сценарии запросов.
```

**Что делает промпт хорошим:**

- конкретные проверяемые пункты, а не «оцени качество»;
- явное указание, что считать ошибкой, а что допустимо с обоснованием;
- ссылка на `{{WORK_DIR}}/README.md`, если у студентов разные варианты.

**Чего избегать:** просьб выставить оценку или вынести вердикт — это
противоречит правилам в `common-footer.md` и даёт противоречивые ответы.

### 3.3. Структурная проверка (опционально)

`check.sh` получает путь к работе, печатает результат в stdout — он попадёт
в промпт. Ненулевой код возврата не роняет workflow, а становится сигналом
для модели.

```bash
#!/usr/bin/env bash
set -uo pipefail
WORK_DIR="${1:?}"
STATUS=0

SQL_COUNT="$(find "${WORK_DIR}" -name '*.sql' | wc -l | tr -d ' ')"
echo "Найдено SQL-файлов: ${SQL_COUNT}"

if [ "${SQL_COUNT}" -eq 0 ]; then
  echo "ВНИМАНИЕ: не найдено ни одного .sql файла."
  STATUS=1
fi

# Если в окружении раннера есть нужный инструмент — можно проверить синтаксис.
if command -v psql >/dev/null 2>&1; then
  echo "--- проверка синтаксиса ---"
  find "${WORK_DIR}" -name '*.sql' -exec psql --no-psqlrc -f {} \; 2>&1 | head -50
fi

exit "${STATUS}"
```

Правила:

- **не полагайтесь на окружение** — у студентов разные стеки; проверяйте
  наличие инструмента через `command -v`;
- **ограничивайте вывод** (`head`) — он идёт в промпт и расходует токены;
- **ставьте таймауты** на запуск студенческого кода (`timeout 120 ...`);
- помните: `check.sh` **выполняет код студента** в раннере. Секреты этому
  шагу не передаются, но полной изоляции нет.

### 3.4. Другое число работ

Папки `tasks/taskN/` — просто соглашение об именах. `detect-task.sh` берёт
номер из ветки `task<N>`; если папки нет, используется `tasks/default/`.
Добавить шестую работу — создать `tasks/task6/prompt.md`.

## 4. Что даёт защиту от списывания

Ключевое: **не ИИ-ревью, а настройки организации**. Ревью — про качество
работы, а не про честность.

| Уровень | Механизм | Доступность |
|---|---|---|
| Изоляция | Base permissions = None, студенты — outside collaborators | Любой план |
| Блокировка `main` | Repository ruleset или branch protection | Ruleset — вероятно на Free; branch protection — Team+ |
| Детект обхода | `guard-main.yml` + `manage.sh audit` | Любой план |

Проверить всё сразу: `./manage.sh doctor`.

> **Про git-хуки.** Их часто предлагают для запрета push в `main`. Не
> работает: server-side pre-receive хуки есть только в GitHub Enterprise
> Server (self-hosted), а клиентские `.git/hooks` не клонируются и обходятся
> через `git push --no-verify`. Поэтому здесь используется ruleset, а где он
> недоступен — детектирующий контроль.

## 5. Ограничения, о которых стоит знать заранее

Честный список — чтобы не было сюрпризов.

1. **Prompt injection полностью не закрыт.** Студент может попытаться
   повлиять на ревью текстом в комментариях кода. Изменения `.github/**`,
   `AGENTS.md`, `opencode.json` блокируются проверкой целостности, а агент
   инструктирован сообщать о таких попытках. Но гарантии нет — читайте
   комментарий бота как подсказку.

2. **Модель ошибается.** Придирается к корректному коду, пропускает реальные
   проблемы. Именно поэтому вердикт запрещён на уровне промпта.

3. **`check.sh` исполняет код студента** в GitHub-раннере. Таймауты есть,
   секреты не передаются, изоляции по контейнеру нет.

4. **Скрипты рассчитаны на приватные репозитории организации.** Для публичных
   Actions бесплатны, но лимиты в `config.env` тогда избыточно строгие.

5. **На Free-плане `main` может остаться незащищённой.** Тогда работает
   только детектирующий контроль.

6. **Общий лимит на группу невозможен.** Из репозитория одного студента не
   видна история чужих, поэтому лимиты — на репозиторий.

## 6. Оценка применимости для вашего курса

| Вопрос | Если «нет» |
|---|---|
| Работы сдаются в виде кода в git? | Система не подойдёт |
| Требования можно описать текстом на 10–15 пунктов? | Промпт будет бесполезно общим |
| Группа до ~25 человек? | Проверьте расчёт минут в `SETUP.md`, раздел 12 |
| Готовы, что ревью иногда ошибается? | Отключите ИИ-ревью, оставьте `guard-main` и `manage.sh` |

Последний вариант вполне рабочий: организационная часть (изоляция
репозиториев, `doctor`, `protect`, `audit`, `broadcast-issue`) полезна и
без ИИ. Тогда просто не создавайте секрет с ключом модели и удалите
`ai-review.yml`.

## 7. Порядок переноса

```
[ ] Прочитать SETUP.md — понять модель и требования
[ ] Скопировать .github/ и admin/ в свой репозиторий
[ ] config.env: COURSE_NAME, COURSE_DOCS
[ ] tasks/: удалить лишние, написать prompt.md под свои работы
[ ] tasks/: при желании написать check.sh
[ ] template-TASK.md: требования вашего практикума
[ ] template-GUIDE.md: правила работы и структура репозитория
[ ] template-README.md: заготовка титульного файла под ваш предмет
[ ] TASKS.md (или аналог): варианты заданий — остаётся у преподавателя
[ ] Развернуть по SETUP.md на тестовой организации
[ ] Прогнать боевую проверку (SETUP.md, раздел 9)
[ ] Проверить, что промпты дают осмысленное ревью на реальной работе
```

Последний пункт важнее прочих: прогоните систему на 2–3 работах прошлого
года и посмотрите, что скажет бот. Промпты почти всегда требуют доводки
после первого столкновения с реальным кодом.

## 8. Проверка после переноса

Собрать промпт локально, без GitHub:

```bash
cd /путь/к/вашему/репозиторию
printf 'test diff\n' > /tmp/d.txt
bash .github/review/lib/build-prompt.sh task1 "." "testuser" 1 /tmp/d.txt
```

Убедитесь, что:

- название курса подставилось;
- не осталось `{{...}}`;
- вывод `check.sh` попал в промпт;
- текст читается как осмысленное задание для модели.

Проверить синтаксис всех скриптов:

```bash
for f in .github/review/lib/*.sh .github/review/tasks/*/check.sh; do
  bash -n "$f" && echo "OK   $f" || echo "FAIL $f"
done
```
