# Отладка промптов и раскатка изменений

Практическое руководство: как менять то, что проверяет ИИ-ревью, убеждаться
что не стало хуже, и доставлять правки студентам.

Общее развёртывание — `SETUP.md`. Перенос на другой курс — `PORTING.md`.

---

## 1. Что где лежит

| Файл | За что отвечает |
|---|---|
| `.github/review/tasks/taskN/prompt.md` | Что проверять в работе №N |
| `.github/review/tasks/taskN/check.sh` | Структурные проверки (наличие файлов, запуск сборки) |
| `.github/review/common-footer.md` | Общие правила: формат ответа, запрет вердикта, защита от инъекций |
| `.github/review/config.env` | Модель, лимиты, название курса |
| `.github/review/messages.env` | Тексты комментариев бота |

Промпт для модели собирается так:

```
tasks/taskN/prompt.md  +  вывод check.sh  +  diff PR  +  common-footer.md
```

Порядок неслучаен: правила идут **после** недоверенных данных студента —
это снижает шанс, что инструкция из кода перебьёт инструкцию курса.

## 2. Цикл правки промпта

### Шаг 1. Посмотреть, что видит модель сейчас

```bash
cd .github/review/tests
./eval-prompts.sh --dry-run
```

Бесплатно, без обращения к API. Показывает размер промпта и проверяет, что
плейсхолдеры раскрыты, а diff помечен как недоверенный.

Чтобы увидеть промпт целиком на своей работе:

```bash
./.github/review/review-local.sh --prompt-only | less
```

### Шаг 2. Зафиксировать текущее качество

**Обязательный шаг.** Без замера «до» вы не отличите улучшение от ухудшения.

```bash
export OPENROUTER_API_KEY=<ключ>
./eval-prompts.sh --repeat 3
```

Запишите результат, например: `broken-task3: 3/3`, `good-task1: 2/3`.

### Шаг 3. Внести правку

Правьте `tasks/taskN/prompt.md` или `common-footer.md`.

Что работает хорошо:

- **конкретные проверяемые пункты** вместо «оцени качество»;
- явное указание, что считать ошибкой, а что допустимо с обоснованием;
- ссылка на `{{WORK_DIR}}/README.md`, если у студентов разные варианты.

Чего избегать:

- просьб выставить оценку — противоречит `common-footer.md`, ответы станут
  противоречивыми;
- слишком длинных промптов — растёт расход токенов, падает фокус модели;
- требований к сложной разметке ответа — бесплатные модели плохо их держат.

### Шаг 4. Прогнать и сравнить

```bash
./run-tests.sh                # структура не сломана (бесплатно, ~5 сек)
./eval-prompts.sh --repeat 3  # качество
```

Сравните с замером из шага 2:

| Было | Стало | Вывод |
|---|---|---|
| 3/3 | 3/3 | Хорошо |
| 3/3 | 2/3 | Насторожиться, повторить с `--repeat 5` |
| 3/3 | 0/3 | Регресс, откатывайте |
| 1/3 | 3/3 | Улучшение |

### Шаг 5. Проверить безопасность

```bash
./eval-prompts.sh injection-task3 --repeat 3
```

Эта фикстура содержит попытку prompt injection. Агент должен отказаться
выполнять инструкцию из кода **и** сообщить о попытке. Ослабление этой
защиты — самый опасный вид регресса, проверяйте после любой правки
`common-footer.md`.

### Шаг 6. Прочитать ответы глазами

```bash
cat .github/review/tests/results/broken-task3.md
```

Автопроверки смотрят на ключевые слова, а не на фактическую точность.
Убедитесь, что бот ссылается на реальные строки и не выдумывает проблемы.

## 3. Как добавить свою фикстуру

Берите реальную работу прошлого года, урезав до нескольких файлов.

```bash
cd .github/review/tests/fixtures
mkdir -p my-case/work
cp -r ../../../../verkovich/examples my-case/work/examples
cp ../../../../verkovich/README.md my-case/work/
```

Опишите ожидания в `my-case/expect.env`:

```bash
TASK_NUM=4
DESCRIPTION="Семантический анализатор без проверки области видимости"

# Обязано встретиться в ревью
EXPECT_PRESENT="область видимости"

# Хотя бы одно из перечисленного
EXPECT_ANY_OF="таблиц.*символ|scope|видимост"

# Не должно встречаться никогда
EXPECT_ABSENT="работа принята|оценка"

MAX_LENGTH_CHARS=8000
```

Проверьте:

```bash
./eval-prompts.sh my-case
```

> Формулируйте ожидания по **сути замечания**, а не по точной фразе.
> Модель каждый раз пишет по-разному; `EXPECT_ANY_OF` с несколькими
> вариантами устойчивее, чем одна жёсткая строка.

## 4. Раскатка изменений студентам

### Порядок

```
правка в этом репозитории
        ↓
   шаблон курса (yapis-2026-template)
        ↓
./manage.sh sync-workflow  →  PR в каждый репозиторий студента
        ↓
   вы мержите PR
```

### Шаг 1. Обновить шаблон

```bash
git clone https://github.com/<ORG>/yapis-2026-template.git /tmp/tmpl
cd /tmp/tmpl

SRC=/путь/к/yapis-2026
rm -rf .github/review
cp -r "$SRC/.github/review" .github/review
cp "$SRC/.github/workflows/"*.yml .github/workflows/

git add -A && git commit -m "review: обновить промпты для лабы 3"
git push
```

### Шаг 2. Разослать по репозиториям

```bash
cd admin
./manage.sh sync-workflow
```

Создаёт PR из ветки `ci/sync-review-tooling` в каждом репозитории студента.
**Автоматически не мержит** — это защита от случайной раскатки.

Что важно знать:

- служебные PR **не расходуют** лимит ревью студента;
- `ai-review` в них отменяется integrity-check — это ожидаемо;
- если изменений нет, репозиторий пропускается.

### Шаг 3. Смержить

```bash
ORG=<ваша-организация>
for r in $(gh repo list "$ORG" --limit 100 --json name --jq '.[].name' | grep '^yapis-2026-' | grep -v template); do
  pr=$(gh pr list --repo "$ORG/$r" --head ci/sync-review-tooling --json number --jq '.[0].number // empty')
  [ -n "$pr" ] && gh pr merge "$pr" --repo "$ORG/$r" --squash --delete-branch
done
```

### Проверка

```bash
ORG=<ваша-организация>
gh api "repos/$ORG/yapis-2026-ivanov/contents/.github/review/config.env" \
  --jq '.content' | base64 -d | grep MODEL
```

### Когда раскатывать

- **Правки промптов** — между лабораторными, не в середине сдачи: студенты
  получат разные замечания на одинаковый код, это выглядит непоследовательно.
- **Исправления багов инфраструктуры** — сразу.
- **Смена модели** — сразу, но сначала проверьте `eval-prompts.sh`.

## 5. Смена модели или провайдера

Поддерживается любой из 200+ провайдеров opencode (см. https://models.dev).
Имя переменной с ключом определяется автоматически, workflow править не нужно.

```bash
# .github/review/config.env
MODEL="anthropic/claude-sonnet-4"
```

```bash
cd admin
./manage.sh set-secret ANTHROPIC_API_KEY
./manage.sh sync-workflow
```

Имя секрета выводится по правилу `<ПРОВАЙДЕР>_API_KEY`; исключения (например,
`google` → `GEMINI_API_KEY`) заданы в `.github/review/lib/provider.sh`.
Если ключ не задан, workflow остановится с понятным сообщением о том, какой
именно секрет нужен.

## 6. Студенты и их собственные модели

Локальный запуск не привязан к модели курса. Студент может использовать свой
ключ, другого провайдера или локальную модель:

```bash
# модель курса (по умолчанию)
./.github/review/review-local.sh

# своя модель разово
./.github/review/review-local.sh --model anthropic/claude-sonnet-4

# постоянно — через переменную окружения в ~/.zshrc
export REVIEW_MODEL=deepseek/deepseek-chat
export DEEPSEEK_API_KEY=...

# локальная модель: без ключей, без интернета, без лимитов
ollama pull qwen2.5-coder
./.github/review/review-local.sh --model ollama/qwen2.5-coder
```

Это влияет **только** на локальный запуск. В Pull Request всегда работает
модель курса — студент не может её подменить.

Вариант с Ollama стоит рекомендовать: он снимает вопрос ключей и квот, а
для черновой проверки структуры работы качества локальной модели достаточно.

## 7. Частые вопросы

**Ревью стало хуже после правки — как откатить?**

```bash
git diff HEAD~1 .github/review/tasks/task3/prompt.md
git checkout HEAD~1 -- .github/review/tasks/task3/prompt.md
```

Затем повторите раскатку через `sync-workflow`.

**Одна фикстура падает, остальные проходят.**

Прогоните `--repeat 5`. Если падает 1-2 раза из 5 — это недетерминированность
модели, а не регресс. Если 5 из 5 — правка ухудшила промпт.

**Модель отвечает не по формату.**

Бесплатные модели держат формат хуже. Варианты: упростить требования в
`common-footer.md`, сменить модель в `config.env`, либо смириться — на
содержательность замечаний это влияет слабо.

**Хочу проверить промпт на реальной работе, а не на фикстуре.**

```bash
cd /путь/к/работе/студента
/путь/к/yapis-2026/.github/review/review-local.sh --task 3
```

**Сколько стоит прогон `eval-prompts.sh`?**

Один запрос к модели на фикстуру. При трёх фикстурах и `--repeat 3` — девять
запросов. На бесплатном тарифе OpenRouter (50/сутки) это заметная доля, но
приемлемая. `--dry-run` бесплатен всегда.
