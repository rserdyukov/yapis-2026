# Развёртывание системы: инструкция для преподавателя

Пошаговая инструкция по запуску автоматической проверки лабораторных работ
для новой группы. Полное развёртывание с нуля занимает около часа, из них
основное время — ожидание одобрения GitHub Education (если оформляете).

Про адаптацию системы под другой предмет — см. `admin/PORTING.md`.

## 1. Что вы получите

**Модель:** одна GitHub-организация на весь курс, внутри — по одному
приватному репозиторию на студента. Студенты добавляются как outside
collaborators и поэтому **не видят репозитории друг друга** — это и есть
защита от списывания.

Группы различаются частью имени репозитория: `yapis-2026-g1-ivanov`,
`yapis-2026-g2-petrov`. Отдельные организации под группы заводить не нужно:

| Что могло бы дать разделение | Даёт ли на самом деле |
|---|---|
| Изоляция студентов | Нет: её обеспечивают base permissions = none и outside collaborators, и они работают внутри одной организации |
| Отдельная квота Actions (2000 мин) | Нет: ревью выполняется централизованно, минуты списываются с аккаунта владельца репозитория ревьюера |
| Отдельная квота модели | Нет: OpenRouter считает лимит free-моделей на аккаунт, а не на ключ — отдельные ключи квоту не удваивают |
| Разные преподаватели | Нет: для этого есть `TEACHERS` и проверка прав через API |

А стоит разделение дорого: по ревьюеру на организацию, двойная раскатка при
каждой правке промптов, несводимая статистика и общий лимит курса, который
невозможно удержать. Единственный реальный аргумент за разделение —
организационный: если коллега должен быть полноправным владельцем своего
хозяйства и не видеть чужие группы.

**Что работает автоматически:**

| Механизм | Что делает |
|---|---|
| Ревьюер | Каждые 10 минут обходит организацию и публикует комментарий с предварительным ИИ-ревью новых коммитов в PR |
| Структурные проверки | Проверяют наличие нужных файлов и прогоняют `compile.sh` студента в контейнере без сети |
| Лимиты | Не дают сжечь бесплатную квоту API и минуты Actions |
| `guard-main` | Ловит push в `main` в обход PR: failing check + issue |
| Защита ветки | Блокирует прямой push в `main`, если тариф позволяет |

Ревью выполняется **не в репозиториях студентов**, а в отдельном приватном
репозитории (раздел 5): так ключ модели не попадает к студентам, минуты
Actions берутся из вашего аккаунта, а лимиты считаются по курсу целиком.

**Что остаётся за вами:** финальное ревью и оценка. ИИ-ревью — только
предварительная подсказка, принять работу оно не может по построению.

## 2. Предварительные требования

### 2.1. Установите GitHub CLI

```bash
# macOS
brew install gh jq

# Ubuntu/Debian
sudo apt install gh jq
```

`jq` обязателен — `manage.sh` использует его для разбора ответов API.

### 2.2. Авторизуйтесь с нужными правами

```bash
gh auth login
gh auth refresh -s admin:org,repo,workflow
```

Права `admin:org` нужны для настроек организации и секретов, `workflow` —
чтобы `sync-workflow` мог обновлять файлы в `.github/workflows/`.

Проверка:

```bash
gh auth status
```

### 2.2.1. Если у вас несколько GitHub-аккаунтов

Частая и неочевидная проблема. Если на машине настроено несколько аккаунтов
(рабочий и личный), git может брать учётные данные не того аккаунта, под
которым авторизован `gh`. Симптом: `gh repo clone` или `git push` в
репозиторий организации отвечает `Repository not found`, хотя доступ есть.

Причина: `gh` по умолчанию работает по SSH, а SSH-ключ для `github.com`
принадлежит другому аккаунту. Либо `credential.helper osxkeychain`
подставляет чужой токен.

Решение — заставить git использовать токен из `gh`:

```bash
gh config set git_protocol https --host github.com
gh auth setup-git
```

Проверить, каким аккаунтом отвечает SSH и HTTPS:

```bash
ssh -T git@github.com                    # покажет, чей ключ используется
gh api user --jq .login                  # под кем авторизован gh
```

Оба должны указывать на аккаунт преподавателя. Если нет — используйте HTTPS
(команды выше): `manage.sh` работает через API `gh`, а `sync-workflow`
дополнительно делает `git clone`/`push`, и ему нужны те же права.

### 2.3. Оформите GitHub Education (рекомендуется, но не обязательно)

Заявка: https://education.github.com/discount_requests/application

Даёт организации план **Team** бесплатно, а с ним:

- защиту ветки `main` для приватных репозиториев;
- 3000 минут Actions в месяц вместо 2000.

> **Проверено на практике.** На плане **Free** защита ветки для приватных
> репозиториев недоступна: и rulesets, и классический branch protection
> отвечают `403 Upgrade to GitHub Pro or make this repository public`.
> Это значит, что без Team/Pro студент технически может запушить в `main`
> или смержить свой PR сам. Документация REST API про repository-level
> rulesets ограничение по тарифу не упоминает, но фактически оно есть.

Одобрение занимает от нескольких часов до нескольких дней. **Систему можно
разворачивать не дожидаясь** — на Free вместо блокировки работает
детектирующий контроль (`guard-main` + `audit`): нарушение не блокируется,
но становится заметным и фиксируется.

## 3. Создание организации

1. Создайте организацию: https://github.com/organizations/plan → **Free**
   (или Team, если Education уже одобрен).
2. Имя выбирайте предсказуемое, например `yapis-2026-group1`.
3. Для второй группы заведите **отдельную организацию** — так студенты разных
   групп гарантированно не пересекаются.

> Одна организация на группу, а не на весь курс: это упрощает выдачу
> доступов и исключает случайное пересечение между группами.

## 4. Настройки организации (критично)

**Это самый важный шаг. Без него защита от списывания не работает вообще.**

Настройки → Member privileges:

| Настройка | Значение | Зачем |
|---|---|---|
| Base permissions | **No permission** | Иначе члены организации видят ВСЕ приватные репозитории |
| Members can create repositories | **выключено** | Чтобы студент не создал публичный репозиторий с решением |

Через CLI — **двумя отдельными запросами**:

```bash
ORG=yapis-2026-group1

gh api -X PATCH "orgs/$ORG" -f default_repository_permission=none
gh api -X PATCH "orgs/$ORG" -F members_can_create_repositories=false
```

> Не объединяйте эти поля в один `PATCH`: GitHub отвечает
> `422 Private-only repository creation policy is not allowed for this
> organization`. По отдельности оба применяются нормально, причём второй
> запрос выставляет и `members_can_create_public_repositories=false`.

Проверить результат:

```bash
gh api "orgs/$ORG" --jq \
  '{plan:.plan.name, base:.default_repository_permission,
    can_create:.members_can_create_repositories}'
# ожидается: base = none, can_create = false
```

Проверить результат можно позже командой `./manage.sh doctor` (шаг 9).

> **Почему это важнее всего остального.** Имена репозиториев предсказуемы
> (`yapis-2026-<фамилия>`). Если base permission = Read, любой член
> организации открывает чужой репозиторий по прямой ссылке и списывает.
> Ни ИИ-ревью, ни защита веток от этого не спасают.

## 5. Ревьюер: GitHub App, ключ модели

ИИ-ревью выполняется **централизованно** — в отдельном приватном
репозитории, а не в репозиториях студентов. По расписанию (каждые 10 минут)
он обходит организацию, находит PR с новыми коммитами и комментирует их от
имени GitHub App.

Почему так:

- **ключ модели не попадает к студентам.** На плане Free организации
  org-секреты не привязываются к приватным репозиториям, поэтому в прежней
  схеме ключ приходилось класть в каждый репозиторий студента — а студент с
  правом `write` мог добавить свой workflow и прочитать его;
- **минуты Actions** расходуются из вашего аккаунта, а не из общей квоты
  организации, которую мог выесть один студент;
- **лимиты считаются по всему курсу сразу**, а не отдельно в каждом
  репозитории;
- **студент не может подменить промпты** и проверки в своей ветке.

### 5.1. Создайте приватный репозиторий ревьюера

```bash
gh repo create rserdyukov/yapis-2026-reviewer --private --add-readme
```

> Репозиторий должен быть **приватным** и лежать **вне организации
> студентов**: в нём хранятся секреты и логи запусков с фрагментами
> студенческого кода. `manage.sh` проверяет это при каждой синхронизации.

### 5.2. Создайте GitHub App

App нужен, чтобы комментарии приходили от бота (`ЯПИС Ревьюер [bot]`), а не
от вашего личного аккаунта, и чтобы токен был короткоживущим (1 час) и с
минимальными правами.

1. Откройте **Organization settings → Developer settings → GitHub Apps →
   New GitHub App** (в организации студентов).
2. Заполните:
   - **Name**: `ЯПИС Ревьюер` (имя увидят студенты в PR);
   - **Homepage URL**: ссылка на публичный репозиторий курса;
   - **Webhook**: снимите галочку **Active** — вебхуки не используются.
3. **Repository permissions**:
   - `Contents` → **Read-only** (клонировать работы);
   - `Pull requests` → **Read and write** (читать PR и комментировать);
   - остальное — **No access**.
4. **Where can this app be installed**: Only on this account.
5. Создайте приложение, затем:
   - запомните **Client ID** (вида `Iv23li...`);
   - нажмите **Generate a private key** — скачается `.pem`-файл;
   - слева **Install App** → установите на организацию → **All repositories**
     (тогда новые репозитории студентов подхватываются автоматически).

### 5.3. Получите ключ OpenRouter

Курс работает с одним провайдером — **OpenRouter**. Ключ нужен один, он
хранится единственным секретом в репозитории ревьюера.

Ключ создаётся здесь: https://openrouter.ai/keys

Лимиты бесплатных моделей (по запросам, **на аккаунт**, а не на ключ):

| Кредиты куплены (за всё время) | Запросов в минуту | Запросов в сутки | Это примерно |
|---|---|---|---|
| Меньше 10 | 20 | 50 | ~6 ревью в сутки |
| От 10 | 20 | 1000 | ~125 ревью в сутки |

Одно ревью — 3–8 запросов: агент читает файлы итеративно, и каждый запрос
несёт всю историю. Промпт сам по себе около 10 КБ (6 000–9 000 токенов).

> **Приватность.** У бесплатных моделей провайдеры могут обучаться на
> промптах, а в промпт попадает код студентов. Обязательно отключите это:
> https://openrouter.ai/settings/privacy → запретить обучение для
> free-моделей.
>
> Студентов стоит предупредить, что их код отправляется внешнему сервису —
> это же требование большинства вузовских политик.

### 5.4. Пропишите настройки ревьюера

```bash
cd admin
cp .env.example .env
$EDITOR .env          # ORG, REVIEWER_REPO, REPO_PREFIX, TEACHERS
```

Переменные и секреты самого репозитория ревьюера:

```bash
R=rserdyukov/yapis-2026-reviewer

# Организация студентов и префикс их репозиториев
gh variable set ORG           --repo "$R" --body "yapis-2026-group1"
gh variable set REPO_PREFIX   --repo "$R" --body "yapis-2026-"

# Client ID приложения из шага 5.2
gh variable set APP_CLIENT_ID --repo "$R" --body "Iv23li..."

# Приватный ключ приложения — целиком, включая строки BEGIN/END
gh secret set APP_PRIVATE_KEY --repo "$R" < ~/Downloads/yapis-reviewer.private-key.pem

# Ключ модели (имя соответствует провайдеру из MODEL)
./manage.sh set-secret OPENROUTER_API_KEY
```

> Скачанный `.pem` после этого удалите: он даёт доступ ко всем репозиториям
> организации. При утере сгенерируйте новый ключ в настройках App.

### 5.5. Раскатайте движок ревью

```bash
./manage.sh sync-reviewer
```

Команда копирует в репозиторий ревьюера промпты, структурные проверки,
скрипты и workflow (состав — `admin/reviewer-manifest.txt`), после чего
ревью начинает работать по расписанию.

Затем соберите образ для изолированного запуска `compile.sh` студентов
(~2 ГБ, около 15 минут, потом пересобирается раз в неделю сам):

```bash
gh workflow run build-check-image.yml --repo "$R"
gh run watch --repo "$R"
```

Проверить, что всё сошлось:

```bash
./manage.sh doctor            # раздел «Ревьюер»
./manage.sh review --dry-run  # покажет, какие PR ревьюер видит
```

### 5.6. Смена модели позже

Меняется одна строка в `.github/review/config.env`, дальше раскатка:

```bash
MODEL="openrouter/google/gemma-4-31b-it:free"
```

```bash
./manage.sh sync-reviewer
```

Модель должна быть из каталога OpenRouter (префикс `openrouter/`): ревьюер
проверяет это и при несовпадении падает с понятным сообщением, а не с
невнятной ошибкой провайдера. Каталог моделей:
https://openrouter.ai/models

> Сменить самого провайдера одной строкой нельзя — это осознанное
> упрощение. Поддержка «любого из 200+ провайдеров» вычисляла имя ключа из
> `MODEL` и на практике только усложняла отладку. Если провайдер всё же
> понадобится поменять, правьте `reviewer/lib/review-pr.sh`, workflow
> ревьюера и `doctor` — это три места.

## 6. Template-репозиторий

Из шаблона создаются все репозитории студентов. В нём лежат только документы
и инструменты студента: инфраструктура ревью живёт у ревьюера (раздел 5).

### 6.1. Создайте репозиторий

```bash
gh repo create rserdyukov/yapis-2026-template --private --add-readme
```

Шаблон удобно держать в личном аккаунте: он общий для всех групп.
Полный путь укажите в `admin/.env` (`TEMPLATE_REPO`).

### 6.2. Наполните его

Содержимое раскатывается из этого репозитория одной командой — вручную
ничего копировать не нужно:

```bash
cd admin
./manage.sh sync-template
```

Состав задаётся файлом `admin/template-manifest.txt`:

| Файл у студента | Источник | Назначение |
|---|---|---|
| `README.md` | `admin/template-README.md` | Титульная страница; заготовка, которую **заполняет студент** описанием своего варианта |
| `TASK.md` | `admin/template-TASK.md` | Требования практикума: список работ, структура отчёта, требования к языку |
| `GUIDE.md` | `admin/template-GUIDE.md` | Как работать: ветки, PR, ИИ-ревью, git |
| `review-local.sh` | `admin/template-review-local.sh` | Локальная проверка: сама скачивает проверки курса в `~/.cache/yapis-review` |
| `.github/workflows/guard-main.yml` | тот же путь | Детектор прямых пушей в `main` |

> Таблица вариантов заданий в шаблон **не копируется** — вариант студент
> получает от преподавателя и выписывает в свой `README.md`. Полный
> `TASKS.md` со всеми вариантами остаётся у вас.
>
> Промпты и структурные проверки студенту тоже не раздаются, но они лежат в
> **публичном** репозитории курса: `review-local.sh` скачивает их оттуда,
> чтобы студент проверялся ровно тем же, чем проверяете вы. Секретом они не
> являются — скрытность промптов ни от чего не защищает.

### 6.3. Включите флаг Template

```bash
gh repo edit rserdyukov/yapis-2026-template --template
```

### 6.4. Проверьте структуру

```bash
gh api repos/rserdyukov/yapis-2026-template/contents --jq '.[].name'
# ожидается: GUIDE.md, README.md, TASK.md, review-local.sh
```

## 7. Настройка manage.sh

```bash
cd admin
cp .env.example .env
```

Заполните `.env`:

```bash
ORG=yapis-2026-group1
TEMPLATE_REPO=yapis-2026-group1/yapis-2026-template
REPO_PREFIX=yapis-2026-
```

> `TEMPLATE_REPO` указывайте полностью, без `${ORG}`: файл читается через
> `source`, и подстановка при незаполненном `ORG` даст неверный путь.

Для двух групп удобно держать два файла и переключаться:

```bash
source .env.group1 && ./manage.sh list
source .env.group2 && ./manage.sh list
```

Проверка:

```bash
./manage.sh list     # пока пусто — это нормально
```

## 8. Создание репозиториев студентов

### 8.1. По одному

```bash
./manage.sh create ivanov ivanov-github-login
```

Команда создаёт приватный репозиторий из шаблона, включает защиту `main`
и приглашает студента с правом Write.

### 8.2. Списком из таблицы (рекомендуется для группы)

Если список студентов ведётся в Google Sheets с колонками
`ФИО | Группа | Github`, выгрузите его в CSV и раскатайте одной командой:

```bash
# ID таблицы и gid листа видны в её URL
ID=1D_gBj_gAPJOdrku4ThHaaoiibLudXsslbMZJ6AfaDAk
GID=1570864661
curl -sL "https://docs.google.com/spreadsheets/d/$ID/export?format=csv&gid=$GID" \
  -o /tmp/students.csv

cd admin
./manage.sh enroll /tmp/students.csv            # план, ничего не меняет
./manage.sh enroll /tmp/students.csv --apply    # выполнить
```

Имя репозитория собирается как `<префикс><группа>-<фамилия транслитом>`:
`yapis-2026-321701-astakhov`. Фамилия берётся из первого слова ФИО.

**Команда безопасна для повторных запусков** — это её главное свойство.
Список заполняется постепенно (логины GitHub появляются не сразу), поэтому
`enroll` рассчитан на многократный вызов:

| Ситуация | Что сделает enroll |
|---|---|
| Репозитория нет | Создаст из шаблона |
| Репозиторий есть | **Не трогает.** Работа студента в безопасности |
| Логина в таблице нет | Создаст репозиторий, пригласит при следующем запуске |
| Логин появился | Только отправит приглашение |
| Студент уже коллаборатор | Ничего |
| Приглашение отправлено, но не принято | Ничего — повторных писем не будет |

Перед изменениями выполняются проверки, и при проблеме команда
останавливается **до** каких-либо действий:

- два студента дают одно имя репозитория (однофамильцы в группе) — ошибка
  с указанием, кого переименовать;
- логин в таблице не существует на GitHub (опечатка) — репозиторий
  создаётся, но приглашение не отправляется, в отчёте будет строка таблицы.

Только одна группа:

```bash
./manage.sh --group 321702 enroll /tmp/students.csv --apply
```

### 8.3. Если логин студента пока неизвестен

Проще всего оставить пустую ячейку в таблице и запустить `enroll` ещё раз,
когда логин появится — он сам поймёт, что репозиторий уже есть, и только
отправит приглашение. Вручную то же самое:

```bash
./manage.sh --group 321701 create ivanov              # создать репозиторий
./manage.sh --group 321701 invite ivanov ivanov-gh    # пригласить позже
```

> **Не добавляйте студентов членами организации.** Только как
> collaborators — это делает `invite`. Если студент случайно окажется
> членом, `doctor` это покажет.

### 8.4. Защита main

`create` включает защиту автоматически. Для уже существующих репозиториев
или после смены тарифа:

```bash
./manage.sh protect          # все репозитории
./manage.sh protect ivanov   # один
```

Команда пробует repository ruleset, при неудаче — классический branch
protection, и честно сообщает, что сработало. Если не сработало ничего
(возможно на Free), это не ошибка: работает `guard-main` + `audit`.

## 9. Проверка перед началом семестра

```bash
./manage.sh doctor
```

Проверяет и объясняет, как исправить:

- план организации;
- `base permissions` = none;
- запрет на создание репозиториев членами;
- нет ли студентов, ошибочно ставших членами организации;
- нет ли публичных репозиториев;
- есть ли активная защита `main` в каждом репозитории;
- настроен ли ревьюер: приватность репозитория, `APP_CLIENT_ID`,
  `APP_PRIVATE_KEY`, секрет с ключом модели, дата последнего запуска;
- не остались ли секреты в репозиториях студентов (след прежней схемы).

Проверка ревьюера избавляет от неприятного сценария: без ключа ревью
падает на последнем шаге, и узнаёте вы об этом из комментария бота об
ошибке на первом же PR студента. Заодно `doctor` проверяет, что `MODEL` в
`config.env` начинается с `openrouter/` — единственного провайдера курса.

**Добейтесь, чтобы критичных проблем не осталось.** Замечание про Free-план
можно оставить — оно информационное.

### Боевая проверка на себе

Прежде чем запускать студентов, прогоните полный цикл на тестовом репозитории:

```bash
./manage.sh create testuser
git clone https://github.com/$ORG/yapis-2026-testuser.git /tmp/t && cd /tmp/t
git checkout -b task1
mkdir -p examples && echo "test" > examples/a.txt
git add -A && git commit -m "test" && git push -u origin task1
gh pr create --title "Лаба 1" --body "проверка" --base main
```

Через несколько минут в PR должен появиться комментарий бота. Если нет —
раздел 11.

Проверьте заодно `guard-main`:

```bash
git checkout main && echo x >> README.md
git commit -am "прямой push" && git push
```

Ожидаемо: либо push отклонён (защита работает), либо появился issue и failing
check (сработал детектирующий контроль). Затем удалите тестовый репозиторий:

```bash
gh repo delete "$ORG/yapis-2026-testuser" --yes
```

## 10. Работа в течение семестра

### Ежедневно / по мере поступления

Открытые PR сами приходят к вам: ревьюер назначает преподавателя группы
ревьюером, и работы собираются в одну очередь на GitHub —
[Pull requests → Review requests](https://github.com/pulls/review-requested).
Обходить репозитории руками не нужно.

```bash
./manage.sh status           # то же самое в консоли, если удобнее
./manage.sh prs              # все открытые PR одной таблицей
```

`prs` отвечает на вопрос «что ждёт проверки дольше всех»: один плоский
список по всем репозиториям, отсортированный по группе, фамилии и дате
последнего коммита — более старые сверху.

```
ГРУППА  СТУДЕНТ         PR  ВЕТКА  СОЗДАН      КОММИТ               ИИ
g1      ivanov          #5  task4  2026-08-20  2026-08-21 (25 дн.)  2
    https://github.com/example-org/yapis-2026-g1-ivanov/pull/5
g1      petrov [draft]  #2  task1  2026-09-05  2026-09-14 (1 дн.)   0 (+1 без ревью)
    https://github.com/example-org/yapis-2026-g1-petrov/pull/2
```

Колонки:

- **КОММИТ** — дата последнего коммита и сколько дней назад он был. Именно
  по ней идёт сортировка, а не по дате создания PR и не по `updatedAt`:
  последний меняется от любого комментария бота и от назначения ревьюера,
  из-за чего свежеотревьюированные работы всплывали бы наверх.
- **ИИ** — сколько ревью бот фактически опубликовал. В скобках, если есть,
  отказы по лимиту и технические сбои: `0 (+1 без ревью)` значит, что бот
  до работы дошёл, но ревью не выдал (упёрся в лимит или PR слишком велик),
  а не «очередь до неё не дошла». Знак `~` перед числом (`~3`) означает, что
  в PR больше комментариев, чем было прочитано, и счётчик — нижняя оценка.

Команда опрашивает репозитории по одному, поэтому на курсе из ~90 человек
занимает около минуты; в терминале виден индикатор прогресса. Пакетный
запрос был бы быстрее, но при этом упёрся бы в лимит сложности GraphQL по
мере роста курса (см. комментарий к `cmd_prs` в `manage.sh`).

Команду можно сузить до одной группы или одного студента — это и быстрее:

```bash
./manage.sh --group g1 prs           # только группа g1
./manage.sh --group g1 prs ivanov    # только один студент
```

Дальше — обычное ревью в PR. Комментарий ИИ читайте как подсказку: он
может ошибаться и придираться. Решение принимаете вы.

### Периодически

```bash
./manage.sh stats            # расход квот и проблемные репозитории
./manage.sh audit            # коммиты в main в обход PR
```

`audit` особенно полезен, если защита `main` недоступна на вашем тарифе.

### Мониторинг расхода квот

```bash
./manage.sh stats                # за последние 30 дней
./manage.sh stats --days 7       # за неделю
./manage.sh stats --json         # машиночитаемо
```

Показывает то, что реально ограничивает работу системы:

| Раздел | Что видно |
|---|---|
| GitHub Actions | Минуты из 2000/мес, запуски, ошибки, разбивка по workflow |
| Квота модели | Расход OpenRouter (если задан `OPENROUTER_API_KEY`) |
| По репозиториям | Минуты, ошибки, опубликованные ревью и отказы по лимитам |
| Требует внимания | Серии неудач, перекос отказов, issue от `guard-main` |

Чтобы увидеть квоту модели, передайте ключ в окружении:

```bash
OPENROUTER_API_KEY=... ./manage.sh stats
```

Ключ используется только в заголовке запроса и в вывод не попадает —
отчёт безопасно вставлять в issue или пересылать коллеге.

> **Про минуты.** Цифра — оценка сверху: GitHub тарифицирует с округлением
> вверх до минуты, а API бесплатного плана не отдаёт точное billable-время.
> Для контроля бюджета этого достаточно, точные данные —
> Organization settings → Billing.

Внешние сервисы мониторинга (Sentry и подобные) для этого проекта не нужны
и плохо подходят: он состоит из shell-скриптов, живущих в ephemeral-job
1–2 минуты, а главные метрики — это квоты GitHub и провайдера модели,
о которых такие сервисы ничего не знают.

### Объявления всем сразу

```bash
echo "Дедлайн по лабораторной работе №3 — 15 октября." > /tmp/msg.md
./manage.sh broadcast-issue "Дедлайн ЛР №3" /tmp/msg.md
```

### Обновление инфраструктуры проверки

Правки вносятся **только в этом репозитории**, дальше расходятся по цепочке:

```
                 ┌── sync-reviewer ──> ревьюер (промпты, проверки, workflow)
yapis-2026 ──────┤
                 └── sync-template ──> шаблон ── sync-workflow ──> студенты
                                                (документы, review-local.sh)
```

```bash
# 1. Убедиться, что ничего не сломано
bash .github/review/tests/run-tests.sh

# 2. Промпты, проверки, скрипты ревью -> репозиторий ревьюера.
#    Нужно после ЛЮБОЙ правки в .github/review/** или reviewer/**,
#    иначе студенты продолжат проверяться старой версией.
cd admin && ./manage.sh sync-reviewer

# 3. Документы студента -> шаблон (коммит прямо в main шаблона)
./manage.sh sync-template

# 4. Шаблон -> репозитории студентов (PR в каждом, сразу мержится;
#    оставить открытым для просмотра: --no-merge)
./manage.sh sync-workflow
```

Что куда попадает, задано манифестами: `admin/reviewer-manifest.txt` и
`admin/template-manifest.txt` — оттуда их читают и команды, и тесты.

Шаги 3–4 нужны, только если менялись документы студента (`TASK.md`,
`GUIDE.md`, `review-local.sh`). Правка промптов или проверок требует
одного шага 2 — у студентов этих файлов нет.

После правки промптов полезно прогнать одно ревью вручную, не дожидаясь
расписания:

```bash
./manage.sh review ivanov:4      # конкретный PR
./manage.sh review --dry-run     # только посмотреть, что ревьюер выберет
```

### Работа с группами

Любую команду можно сузить до одной группы:

```bash
./manage.sh --group g1 status        # PR только группы g1
./manage.sh --group g1 audit         # проверка коммитов только g1
./manage.sh --group g1 review        # прогнать ревью только для g1
./manage.sh status                   # все группы сразу
```

Фильтр — это префикс имени репозитория, поэтому `--group g1` означает
«репозитории, начинающиеся на `yapis-2026-g1-`». При создании репозитория
группа подставляется в имя автоматически:

```bash
./manage.sh --group g1 create ivanov ivanov-gh   # -> yapis-2026-g1-ivanov
```

Если группу нужно использовать постоянно, её можно задать в `admin/.env`
(`GROUP=g1`), но обычно удобнее работать сразу по всему курсу.


## 10.1. Несколько преподавателей

Система нигде не привязана к конкретному GitHub-аккаунту, поэтому коллегу
достаточно добавить в трёх местах. Отдельная организация ему не нужна —
почему, см. раздел 1.

### 1. Владелец организации

```bash
gh api -X PUT "orgs/yapis-2026/memberships/<логин-коллеги>" -f role=admin
```

Роль `admin` нужна не ради статуса: `guard-main` определяет доверенность по
фактическим правам в репозитории, а не по логину. Без неё push коллеги в
`main` будет отмечен как нарушение, а issue создастся на пустом месте.

### 2. Список TEACHERS

В `admin/.env` **у обоих** преподавателей:

```bash
TEACHERS=rserdyukov,petrov-teacher
```

Скрипт знает только того, кто его запустил. Без этого списка `./manage.sh
audit` покажет коммиты коллеги как подозрительные, а `./manage.sh doctor` —
его членство в организации как ошибочно добавленного студента.

Регистр не важен. Можно добавить и имя из git-конфига, если оно отличается
от логина (`TEACHERS=rserdyukov,Пётр Петров`) — `audit` сверяет обе формы.

> Проверить, что всё применилось: `./manage.sh doctor`. Коллега должен
> появиться в списке «Члены организации», но **не** в списке «Студенты,
> ошибочно добавленные как члены организации» — последнее означает, что его
> забыли внести в `TEACHERS`.

### 3. Доступ к ревьюеру (по необходимости)

Если коллега должен сам запускать ревью и смотреть логи:

```bash
gh api -X PUT "repos/rserdyukov/yapis-2026-reviewer/collaborators/<логин>" \
  -f permission=push
```

Это не обязательно: ревью идёт по расписанию и работает независимо от того,
у кого есть доступ к репозиторию ревьюера. Но без доступа коллега не сможет
ни перезапустить упавшее ревью, ни посмотреть причину сбоя.

> **Осторожно:** в этом репозитории лежат ключ модели и приватный ключ
> GitHub App. Давайте доступ только тому, кому доверяете эти секреты.
> Права `push` достаточно — `admin` позволит менять секреты.

### Работа по группам

Дальше каждый работает со своей группой через фильтр:

```bash
./manage.sh --group g2 status
./manage.sh --group g2 create petrov petrov-gh
```

Ключ модели и квота при этом общие на курс — это неизбежно (лимит
OpenRouter действует на аккаунт, а не на ключ, см. раздел 12). Поэтому
`MAX_REVIEWS_PER_DAY_TOTAL` в `config.env` — это общий бюджет на всех, и
согласовывать его нужно вдвоём.

### Что НЕ требует изменений

- `.github/workflows/**` — доверенность определяется по правам в
  репозитории, а не по логину;
- `manage.sh` — работает с той организацией, что указана в `.env`;
- шаблон и промпты — общие для всех;
- ревьюер — один на курс, обходит все группы сразу.

### Кто получает PR на проверку

Единственное, что нужно поделить между преподавателями явно, — назначение
ревьюера. Оно задаётся в `.github/review/config.env`:

```bash
TEACHER_BY_GROUP="321701:rserdyukov 321702:rserdyukov 321703:kvetkod"
TEACHER_DEFAULT=""     # для групп, не перечисленных выше
```

Ревьюер по расписанию проставляет review request на преподавателя группы, и
работа попадает в его личный список **Pull requests → Review requests** —
одна очередь на все группы. Подробнее — раздел 10.2.

После правки: `./manage.sh sync-reviewer`.

## 10.2. Назначение преподавателя ревьюером PR

Открытый PR студента автоматически получает review request на преподавателя
его группы. Смысл в том, чтобы работа не терялась: назначенный ревьюер
ставит PR в раздел [Review requests](https://github.com/pulls/review-requested)
— единую очередь работ на проверку по всем группам, вместо обхода
репозиториев руками или поиска писем в почте.

### Настройка

Кто какую группу ведёт — `.github/review/config.env`:

```bash
# Группа — часть имени репозитория после REPO_PREFIX
# (yapis-2026-321701-ivanov -> 321701).
TEACHER_BY_GROUP="321701:rserdyukov 321702:rserdyukov 321703:kvetkod"

# Преподаватель для групп, не перечисленных выше. Пустое значение —
# не назначать никого. Если преподаватель один, удобнее заполнить только это.
TEACHER_DEFAULT=""
```

После правки раскатайте в ревьюер: `./manage.sh sync-reviewer`.

Преподаватель обязан иметь доступ к репозиториям своей группы: GitHub
отклоняет запрос ревью у не-коллаборатора. У нас оба преподавателя —
админы организации, доступ выдаётся при `enroll`/`create`. Проверить:
`./manage.sh doctor` (раздел «Назначение преподавателя ревьюером PR»).

### Как это работает

Назначение делает ревьюер — та же job, что и ИИ-ревью, но **независимая**
от него (`reviewer/lib/assign-reviewers.sh`, job `assign-reviewers` в
`reviewer/workflow/review.yml`). Независимость важна: лимиты ИИ-ревью
(дневная квота модели, размер diff, `MAX_REVIEWS_PER_PR`) не должны мешать
работе попасть к преподавателю.

Скрипт идемпотентен и запускается по расписанию каждые 10 минут. Не
назначает повторно, если ревью уже запрошено или преподаватель уже его
оставил: повторный запрос — это кнопка «Re-request review» у преподавателя,
а не задача автоматики. Пропускает draft-PR (работа ещё не сдана) и
служебные ветки `ci/*` (их создаёт `sync-workflow`).

Вне расписания, когда результат нужен сразу:

```bash
./manage.sh assign-reviewers --dry-run     # показать, что будет сделано
./manage.sh assign-reviewers               # по всем репозиториям
./manage.sh assign-reviewers ivanov        # только один студент
./manage.sh --group 321703 assign-reviewers
```

### Почему не CODEOWNERS

Штатный механизм GitHub — файл `.github/CODEOWNERS` в репозитории студента.
На плане Free для **приватных** репозиториев он не работает: файл
принимается без ошибок (`GET /repos/{owner}/{repo}/codeowners/errors`
возвращает пустой список), но при открытии PR ревьюер не запрашивается —
`requested_reviewers` остаётся пустым. Проверено экспериментально на
отдельном репозитории организации.

Кроме того, CODEOWNERS в репозитории студента редактируется самим студентом
(у него есть write), а раскатывать его пришлось бы отдельным PR на каждую
группу — файл содержит логин преподавателя, то есть у групп он разный.

Если организация перейдёт на план Team (GitHub Education, см. раздел 1),
CODEOWNERS заработает, и его можно будет добавить в шаблон вместо этого
скрипта — вместе с обязательным ревью в защите ветки `main`.

## 11. Диагностика проблем

### ИИ-ревью не появилось в PR

Проверьте по порядку:

Сначала общая диагностика — она покрывает почти все случаи:

```bash
./manage.sh doctor
./manage.sh review --dry-run    # что ревьюер видит прямо сейчас
```

Затем логи самого ревьюера (в репозитории ревьюера, не у студента):

```bash
R=rserdyukov/yapis-2026-reviewer
gh run list --repo "$R" --workflow review.yml --limit 5
gh run view <RUN_ID> --repo "$R" --log-failed
```

Частые причины:

| Симптом | Причина | Решение |
|---|---|---|
| Ревьюер ни разу не запускался | Движок не раскатан | `./manage.sh sync-reviewer` |
| В логе «Репозиториев студентов не найдено» | Неверные `ORG`/`REPO_PREFIX` у ревьюера | `gh variable set ORG --repo "$R" --body ...` |
| В логе 404/403 при обращении к репозиторию | GitHub App не установлен на организацию или установлен не на все репозитории | Install App → All repositories |
| Комментарий «пропущено: лимиты» | Исчерпан дневной лимит | Норма. Правьте `config.env`, если мешает |
| В шапке ревью «Сокращённый режим» | Diff (без сгенерированных файлов) больше `MAX_DIFF_LINES` | Норма: compile.sh/грамматика проверены, код смотрит преподаватель |
| Комментарий «техническая ошибка» | Сбой модели или контейнера проверок | Смотрите лог; повторить: `./manage.sh review <репо>:<PR>` |
| Ошибка авторизации модели | Секрет не задан или истёк | `./manage.sh set-secret <КЛЮЧ_ПРОВАЙДЕРА>` |
| В логе «Образ недоступен» | Не собран образ проверок | `gh workflow run build-check-image.yml --repo "$R"` |

> Ревью по расписанию запускается каждые 10 минут, но GitHub при нагрузке
> может пропускать запуски cron. Задержка до получаса — это нормально; если
> нужно срочно, запустите вручную: `./manage.sh review ivanov:4`.

### PR студента не появился в «Review requests»

Назначение ревьюера — отдельная job ревьюера, не зависящая от ИИ-ревью
(раздел 10.2). Диагностика:

```bash
./manage.sh doctor                          # раздел про назначение ревьюером
./manage.sh assign-reviewers --dry-run      # что видит скрипт прямо сейчас
```

| Симптом | Причина | Решение |
|---|---|---|
| «не задан преподаватель» | Группы нет в `TEACHER_BY_GROUP` | Добавить группу, затем `./manage.sh sync-reviewer` |
| «не удалось определить группу» | Имя репозитория не по схеме `<префикс><группа>-<фамилия>` | Переименовать репозиторий либо задать `TEACHER_DEFAULT` |
| «НЕ УДАЛОСЬ назначить» | У преподавателя нет доступа к репозиторию | `./manage.sh invite` либо добавить его админом организации |
| «draft, пропускаю» | Студент не нажал «Ready for review» | Норма: draft-PR не считается сданной работой |
| Назначение не повторилось после нового коммита | Так задумано | Повторный запрос — кнопка «Re-request review» в PR |

### Ревью приходит не от бота, а от вашего имени

Значит, вместо GitHub App используется ваш токен. Проверьте, что в
репозитории ревьюера заданы `APP_CLIENT_ID` и `APP_PRIVATE_KEY`, и что App
установлен на организацию (раздел 5.2).

### Кончились минуты Actions

Organization settings → Billing. При исчерпании квоты workflow не запускаются
вовсе. Варианты: снизить `MAX_REVIEWS_PER_PR` до 1 в `config.env`, либо
оформить Education (Team = 3000 минут).

### Студент не видит свой репозиторий

Приглашение приходит письмом и живёт 7 дней. Повторить:

```bash
./manage.sh invite ivanov ivanov-gh
```

### Студент видит чужие репозитории

Критично. Немедленно:

```bash
./manage.sh doctor
```

Скорее всего, `base permissions` не `none` или студент стал членом
организации. Оба случая `doctor` покажет с инструкцией по исправлению.

## 12. Бюджеты и лимиты

### GitHub Actions

| План | Минут в месяц (на всю организацию) |
|---|---|
| Free | 2000 |
| Team (в т.ч. по Education) | 3000 |

Расход считается только для приватных репозиториев. **Важно:** минуты
ревьюера списываются с того аккаунта, где лежит его репозиторий (ваш
личный — 2000 минут в месяц), а не с квоты организации.

Ориентировочно на группу 20 человек:

| Статья | Расход |
|---|---|
| Ревью работ: 20 × 5 работ × 2 ревью × ~3 мин | ≈ 600 минут за семестр |
| Обход по расписанию: 144 запуска в сутки × ~0,3 мин | ≈ 45 минут в сутки |

Обход по расписанию — основная постоянная статья. Если минут не хватает,
увеличьте интервал cron в `reviewer/workflow/review.yml` с `*/10` до
`*/20` или `*/30`: студенты получат ревью чуть позже, расход упадёт вдвое-втрое.

Следить за расходом: `./manage.sh stats`.

### Лимиты ИИ-ревью

Настраиваются в `.github/review/config.env`:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `MAX_REVIEWS_PER_PR` | 3 | Опубликованных ревью на один PR (первичное, после правок, контроль) |
| `MAX_REVIEWS_PER_DAY` | 4 | Ревью в сутки в одном репозитории студента |
| `MAX_REVIEWS_PER_DAY_TOTAL` | 40 | Ревью в сутки на весь курс (на платной модели ограничивает только бюджет Actions) |
| `MAX_REVIEWS_PER_RUN` | 4 | Сколько PR проверяется за один запуск по расписанию |
| `MAX_DIFF_LINES` | 5000 | Больше — сокращённый режим: проверки запускаются, анализ кода пропускается |
| `MAX_DIFF_LINES_IN_PROMPT` | 6000 | Строк diff в промпте; остальное агент дочитывает `read` |
| `MAX_PROMPT_BYTES` | 400000 | Потолок промпта; при превышении доля diff уменьшается вдвое |
| `AGENT_TIMEOUT_SECONDS` | 900 | Таймаут одного запуска агента |
| `DEPS_TIMEOUT_SECONDS` | 300 | Таймаут фазы установки зависимостей (с сетью, без секретов) |
| `CHECK_TIMEOUT_SECONDS` | 300 | Таймаут фазы проверки (`check.sh` → `compile.sh`, без сети) |

Отдельного cooldown больше нет: повторное ревью не запускается, пока в PR
не появится новый коммит (ревьюер помечает проверенный SHA в комментарии).

**Сгенерированные файлы** (вывод ANTLR `<Grammar>Lexer.py`/`<Grammar>Parser.py`,
`*.interp`, `*.tokens`, `__pycache__/`, `target/`, `node_modules/` и т.п. —
список в `lib/generated-files.sh`) не считаются в `MAX_DIFF_LINES` и не
попадают в diff для модели. Их перечень идёт в промпт отдельной секцией:
коммит сгенерированного — замечание. Раньше один Python-парсер ANTLR на
4000 строк переводил PR в «слишком большой» и студент оставался без
проверки `compile.sh` вовсе.

**Сокращённый режим.** Если и без сгенерированных файлов PR больше
`MAX_DIFF_LINES`, ревью не отменяется: `check.sh` (compile.sh на примерах,
сборка грамматики) выполняется как обычно, а модель получает только его
вывод и список файлов — без diff, с запретом читать исходники. В шапке
комментария появляется предупреждение «Сокращённый режим», а ответ модели
начинается с фразы «Анализ кода пропущен из-за размера PR».

### Квота модели

Лимит бесплатных моделей OpenRouter зависит от того, покупались ли когда-либо
кредиты на аккаунте:

| Кредиты куплены (за всё время) | Запросов в минуту | Запросов в сутки | Это примерно |
|---|---|---|---|
| Меньше 10 | 20 | **50** | ~6 ревью в сутки |
| От 10 | 20 | **1000** | ~125 ревью в сутки |

Одно ревью — 3–8 запросов: агент работает итеративно, читая файлы. Лимит
считается **на аккаунт**, а не на ключ: заводить отдельные ключи под группы
бессмысленно, квоту это не увеличит
([документация](https://openrouter.ai/docs/api-reference/limits)).

Проверить текущий тариф и остаток:

```bash
export OPENROUTER_API_KEY=<ваш ключ>
./manage.sh stats
```

В разделе «Квота модели» будет `Тариф: бесплатный (кредиты не покупались)`
или `Тариф: платный`, а также фактический дневной лимит. После пополнения
аккаунта на 10 кредитов строка меняется на «платный», и `stats` сам
подскажет, что `MAX_REVIEWS_PER_DAY_TOTAL` в `config.env` можно поднять.

> Пополнение меняет только лимит **бесплатных** моделей (`:free`). Деньги с
> баланса при этом не списываются: `:free`-варианты бесплатны всегда.
> Учтите комиссию платформы при покупке кредитов — 5.5% (минимум $0.80),
> то есть для порога в 10 кредитов пополнять нужно с запасом.
>
> Кредиты сгорают через год после покупки, если не израсходованы.

Лимит на PR считается по **опубликованным** комментариям: отказы по cooldown
бюджет не расходуют.

> Общий лимит на группу технически невозможен: из репозитория одного студента
> не видна история чужих. Поэтому лимиты — на репозиторий, и заданы
> консервативно.

### Лимиты провайдера модели

Одно ревью расходует примерно **80 000–200 000 токенов** за 5–15 запросов:
промпт теперь обязывает агента читать README и файлы чеклиста
инструментами, и каждый запрос несёт всю историю. Промпт с diff — 20–60 КБ
(15 000–40 000 токенов). На gemma-4-31b ($0.09/M вход) это $0.01–0.02 за
ревью; на 300 ревью в семестр — до $6.

| Тариф аккаунта OpenRouter | Лимит | Хватает на |
|---|---|---|
| Кредиты не покупались | 20 запросов/мин, 50/сутки | ~6 ревью в сутки |
| Куплено от 10 кредитов | 20 запросов/мин, 1000/сутки | ~125 ревью в сутки |

Квота общая **на аккаунт**, а не на ключ и не на репозиторий: заводить
отдельные ключи под группы бессмысленно. Ваш собственный потолок задаёт
`MAX_REVIEWS_PER_DAY_TOTAL` в `config.env` — держите его ниже квоты
провайдера с запасом на повторы.

Актуальные лимиты: https://openrouter.ai/docs/api-reference/limits

При превышении workflow завершится ошибкой и оставит соответствующий
комментарий в PR — ревью в этом случае делаете вы.
