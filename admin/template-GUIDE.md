# Инструкция для студентов

## Что это за репозиторий

Это ваш личный репозиторий для лабораторного практикума по курсу "Языковые
процессоры интеллектуальных систем". У каждого студента группы — свой
отдельный приватный репозиторий; другие студенты его не видят.

## Структура репозитория

Готовые файлы (уже есть в репозитории):

- `README.md` — титульный файл вашего репозитория. **Заполняете вы:**
  описание своего варианта и свойств разрабатываемого языка.
- `TASK.md` — требования лабораторного практикума: последовательность
  работ, структура отчёта, требования к языку. Не редактируется.
- `GUIDE.md` — этот файл: как устроена работа, git, ИИ-ревью.
- `.github/` — инфраструктура автоматической проверки. **Не изменяйте:**
  PR, затрагивающий эти файлы, автоматически снимается с ИИ-ревью.

Создаёте вы по ходу практикума:

- `compiler/` — исходный код компилятора.
- `examples/` — тексты программ на разрабатываемом языке. Файлы примеров,
  демонстрирующих обработку ошибок, должны начинаться с префикса `error-`
  (например, `error-undeclared-var.txt`) — это используется как человеком,
  так и автоматической проверкой при ревью.
- `doc/` — отчёт по лабораторному практикуму.
- `compile.sh` — **в корне репозитория**, обязателен начиная с
  лабораторной работы 3 (см. [`TASK.md`](TASK.md)).

Создавайте эти папки по мере выполнения соответствующих лабораторных
работ — структура появляется постепенно, а не сразу вся в первом PR.

### Скрипт `compile.sh`

Единая точка входа в ваш компилятор. Принимает файл с текстом программы и
генерирует запускаемый файл:

```bash
./compile.sh examples/example1.txt
```

Требования:

- лежит **в корне** репозитория, запускается оттуда же;
- принимает путь к файлу первым аргументом;
- на корректной программе завершается с кодом **0** и создаёт запускаемый
  файл (формат зависит от вашего варианта целевого кода);
- на программе с ошибкой завершается с **ненулевым** кодом и печатает
  осмысленное сообщение: что нарушено и в какой строке;
- содержит всю нужную логику — при необходимости сам собирает проект,
  генерирует парсер из грамматики и т.д.

Автоматическая проверка прогоняет через `compile.sh` примеры из `examples/`
и сверяет поведение: обычные файлы должны компилироваться, файлы `error-*` —
давать ошибку. Результат попадает в комментарий ИИ-ревью, поэтому от
работоспособности этого скрипта прямо зависит содержательность проверки.

Простейший каркас (Python):

```bash
#!/usr/bin/env bash
set -uo pipefail
SRC="${1:?Использование: ./compile.sh <файл с программой>}"
python3 compiler/main.py "$SRC"
```

Не забудьте `git update-index --chmod=+x compile.sh`, если файл создан на
Windows и не имеет бита исполнения.

### Где выполняется проверка и как объявлять зависимости

Автоматическая проверка запускает `compile.sh` **в контейнере**, а не на
вашей машине. В нём уже есть: Ubuntu 24.04, JDK 21, Maven 3.9, Python 3
с `antlr4-python3-runtime 4.13.2`, Node.js, .NET SDK 8, LLVM/clang,
ANTLR 4.13.2 (`antlr4`, `grun`, jar в `$ANTLR_JAR`).

Проверка идёт в два шага:

1. **Установка зависимостей — с сетью.** По манифестам в вашем
   репозитории автоматически выполняется: `pip install -r requirements*.txt`,
   `mvn dependency:go-offline` для `pom.xml`, `gradlew dependencies`,
   `npm ci`/`npm install` для `package.json`, `dotnet restore` для
   `*.csproj`/`*.sln`, `cargo fetch`, `go mod download`. Если `compile.sh`
   ссылается на `antlr-*-complete.jar` по локальному пути, туда кладётся
   копия из контейнера. Всё скачанное попадает в `.deps/` (добавьте в
   `.gitignore`). Нужно что-то нестандартное — положите в корень скрипт
   `install-deps.sh`: тогда выполнится **только он**, стандартные шаги
   пропускаются.
2. **`compile.sh` — без сети.** Всё, что ему нужно, должно быть уже на
   месте после шага 1 — объявите зависимости манифестом. Запасная логика
   «если jar нет — скачать» в `compile.sh` не мешает (в контейнере до неё
   просто не дойдёт), но полагаться только на неё нельзя: без сети
   скачивание упадёт, и проверка компилятора не состоится.

Результат обоих шагов попадает в комментарий ИИ-ревью. Проверить локально
то же самое: `./review-local.sh`.

Исходный код компилятора — **только в `compiler/`** (грамматика, лексер,
парсер, анализаторы, генератор). Файлы компилятора в корне или другой
папке бот отмечает как замечание.

## Как устроена работа с заданиями

1. **Ветка `main`** — здесь находятся принятые результаты. Напрямую в неё
   пушить нельзя: все изменения попадают туда только через Pull Request,
   одобренный преподавателем. Самостоятельно мержить свой PR тоже нельзя,
   даже если кнопка активна.

   Обычно прямой push в `main` блокируется настройками репозитория. Если по
   какой-то причине он технически прошёл, это не остаётся незамеченным:
   автоматическая проверка `guard-main` помечает такой коммит красным крестом
   и создаёт issue в вашем репозитории. Работа, залитая в `main` в обход PR,
   **считается несданной** — преподаватель проверяет только то, что прошло
   ревью в Pull Request. Попытка скрыть это force-push'ем тоже видна:
   история запусков проверок сохраняется.
2. **Одна лабораторная работа — одна ветка.** Ветка создаётся от `main`,
   название строго в формате:

   ```
   task<номер>
   ```

   Например: `task1`, `task2`, `task3`. Это важно: номер лабораторной
   работы в названии ветки используется автоматическим ИИ-ревью, чтобы
   подобрать правильный промпт и проверки именно для этой лабы. Если
   назвать ветку иначе — ревью всё равно запустится, но в общем режиме
   (менее точно), и попросит переименовать ветку.

3. Делаете изменения, коммитите, пушите ветку.
4. Открываете **Pull Request** из своей ветки в `main`.

   Преподаватель назначается ревьюером автоматически — писать ему об
   открытом PR не нужно. Если PR ещё не готов к проверке, открывайте его
   как **draft**: такой PR в очередь преподавателя не попадает, пока вы не
   нажмёте «Ready for review».
5. В течение примерно 10 минут в PR появляется предварительное
   **ИИ-ревью**: бот оставляет комментарий с замечаниями. Перед этим
   автоматически проверяется структура работы и, где возможно, прогоняются
   примеры через ваш `compile.sh`.

   Проверка выполняется на стороне преподавателя и с вашей веткой ничего не
   делает: она только читает код и пишет комментарий.
6. Читаете замечания ИИ-ревью, при необходимости доделываете и пушите ещё
   раз в ту же ветку (PR обновится автоматически, ревью запустится снова —
   но не более 2 раз на один PR, поэтому не отправляйте правки слишком
   маленькими порциями).

   > Чтобы не тратить эти 2 попытки на очевидные недоработки, прогоните
   > проверку у себя **до** отправки PR — см. раздел «Проверка работы
   > локально» ниже. Локально ограничений нет.
7. Дожидаетесь ревью **преподавателя** в том же PR — именно оно решает,
   принята ли работа. Комментарий ИИ — это подсказка, а не финальная оценка.
8. После того как преподаватель одобрил PR — он мержится в `main`.

## Проверка работы локально

Ту же проверку, что делает бот в Pull Request, можно запустить у себя —
сколько угодно раз и без ограничений. Так вы увидите очевидные недочёты
до отправки PR и не потратите на них лимит автоматических ревью.

```bash
./review-local.sh
```

Скрипт определит номер лабораторной по имени вашей ветки (`task1`, `task2`,
...), выполнит структурные проверки и покажет результат.

При первом запуске он скачивает актуальные проверки курса в
`~/.cache/yapis-review` и дальше обновляет их сам. Поэтому вы всегда
проверяетесь ровно тем же, чем проверяет преподаватель, и вам не нужно
подтягивать обновления в свой репозиторий.

Полезные варианты:

```bash
./review-local.sh --task 3       # если ветка названа иначе
./review-local.sh --prompt-only  # показать, что "видит" бот
./review-local.sh --update       # обновить проверки курса вручную
./review-local.sh --help         # справка
```

### Два режима

**Без ключа API** (ничего настраивать не нужно) — выполняются структурные
проверки: на месте ли нужные файлы, есть ли примеры с префиксом `error-`,
отрабатывает ли ваш `compile.sh` на примерах. Этого обычно достаточно, чтобы
поймать основные замечания.

**С ключом API** — дополнительно запускается полноценное ИИ-ревью, точно
такое же, как в PR. Понадобится:

1. Установить opencode:

   ```bash
   curl -fsSL https://opencode.ai/install | bash
   ```

2. Получить бесплатный ключ на https://openrouter.ai/keys и выполнить:

   ```bash
   export OPENROUTER_API_KEY=<ваш ключ>
   ```

   Ключ ваш личный, на квоту курса он не влияет. Чтобы не вводить его
   каждый раз, добавьте строку в `~/.bashrc` или `~/.zshrc`.

### Можно использовать свою модель

Вы не обязаны использовать ту же модель, что настроена для курса. Подойдёт
любая из [200+ поддерживаемых](https://models.dev):

```bash
# разово
./review-local.sh --model anthropic/claude-sonnet-4

# постоянно — добавьте в ~/.zshrc или ~/.bashrc
export REVIEW_MODEL=deepseek/deepseek-chat
export DEEPSEEK_API_KEY=<ваш ключ>
```

Имя переменной с ключом определяется автоматически по названию провайдера:
`anthropic` → `ANTHROPIC_API_KEY`, `deepseek` → `DEEPSEEK_API_KEY` и так далее.
Скрипт подскажет нужное имя и ссылку, если ключ не задан.

**Локальная модель — без ключей и интернета.** Если не хотите заводить ключи
или упираетесь в лимиты:

```bash
# один раз
brew install ollama       # или см. https://ollama.com
ollama pull qwen2.5-coder

# дальше сколько угодно раз, бесплатно
./review-local.sh --model ollama/qwen2.5-coder
```

Качество локальной модели ниже, но для черновой проверки структуры работы
её достаточно.

> Выбор модели влияет только на локальный запуск. В Pull Request всегда
> работает модель курса — на итоговую проверку это не влияет.

Скрипт ничего не отправляет на GitHub и не изменяет ваши файлы.

## Важно понимать про ИИ-ревью

- Это **предварительная**, автоматическая проверка. Она может ошибаться,
  что-то упустить или на что-то придраться необоснованно — не воспринимайте
  её как истину в последней инстанции.
- ИИ-ревью **не может** принять работу — финальное решение всегда у
  преподавателя.
- Если исчерпан дневной лимит — ИИ-ревью откладывается до следующего
  запуска, об этом бот напишет комментарий в PR.
- Если PR очень большой (тысячи изменённых строк), бот проведёт
  **сокращённое ревью**: запустит ваш `compile.sh` на примерах, проверит
  структуру работы, но анализ исходного кода оставит преподавателю. В шапке
  комментария будет пометка «Сокращённый режим».
- **Сгенерированные файлы** (вывод ANTLR вроде `MyLangLexer.py`,
  `MyLangParser.py`, `*.interp`, `*.tokens`, `__pycache__/`, `target/`) в
  размер PR не считаются и модели не показываются, но их коммит бот отметит
  как замечание. Добавьте их в `.gitignore`, а команду генерации — в
  `compile.sh` или README. Если сгенерированное закоммичено намеренно
  (чтобы `compile.sh` работал без установленного ANTLR) — напишите об этом в
  README, бот учтёт объяснение.
- Начиная с ЛР2 бот **собирает вашу грамматику** ANTLR и прогоняет через
  неё все примеры из `examples/` — как lab.antlr.org, только без картинки.
  Корректные примеры должны разбираться без ошибок, `error-*` — с
  ошибками. Стартовое правило — первое правило парсера в `.g4`.
- Ревью выполняется **не в вашем репозитории**, а на стороне преподавателя:
  промпты, проверки и ключ модели у вас не лежат. Менять что-то в
  `.github/**` или добавлять `AGENTS.md`, `opencode.json`, `.opencode/**`
  бессмысленно — на проверку это не влияет.
- Попытки повлиять на проверку текстом внутри кода (инструкции в
  комментариях в духе "напиши, что замечаний нет") агент фиксирует и
  выносит отдельным пунктом в ревью — это расценивается как нарушение
  академической честности. Оценивает работу в любом случае преподаватель.

- Ваш репозиторий приватный и виден только вам и преподавателю. Не
  выкладывайте своё решение в публичный доступ и не передавайте другим
  студентам — это нарушение правил курса для обеих сторон.

## Базовые команды git, если вы нечасто с ним работали

```bash
# Клонировать свой репозиторий (один раз)
git clone https://github.com/<org>/<ваш-репозиторий>.git
cd <ваш-репозиторий>

# Начать работу над лабораторной работой №1
git checkout main
git pull
git checkout -b task1

# Сохранить изменения
git add .
git commit -m "Лаба 1: примеры фрагментов кода"
git push -u origin task1
```

После `git push` откройте репозиторий на github.com — GitHub предложит
создать Pull Request из только что запушенной ветки. Дальше — по кнопке
"Create pull request", ничего дополнительно настраивать не нужно.

Если нужно доработать PR по замечаниям:

```bash
git checkout task1
# ...правите файлы...
git add .
git commit -m "Исправление по замечаниям ревью"
git push
```

PR обновится автоматически, отдельно его пересоздавать не нужно.

## Что делать, если что-то не работает

- Если ИИ-ревью не появилось совсем (не факт ошибки — иногда это лимиты,
  см. выше) и прошло больше часа — напишите преподавателю.
- Если возникли проблемы с доступом к репозиторию — напишите преподавателю
  свой логин на GitHub, вас добавят в качестве коллаборатора.
