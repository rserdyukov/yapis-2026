# Go: сознательная бедность языка

*Каждая возможность языка стоит времени читателю, автору компилятора и авторам инструментов; Go принимает это всерьёз и включает меньше, чем мог бы.*

## Проблема

Обычно язык развивается в одну сторону: версия за версией он получает новые
возможности и почти никогда их не теряет. Каждая возможность по отдельности
удобна. Но в большой кодовой базе, над которой одновременно работают сотни
людей, в итоге получается, что разные программисты пишут на разных подмножествах
языка, код трудно читать без контекста, а инструменты (форматтеры, рефакторинг,
анализаторы) приходится писать под грамматику, которую тяжело разбирать.

[Роб Пайк](../languages/people.md#pike) в докладе
[«Go at Google: Language Design in the Service of Software Engineering»](https://go.dev/talks/2012/splash.article)
(SPLASH 2012, [в списке источников](../languages/sources.md#pike-go-at-google))
перечисляет, что мешало разработке серверного ПО в Google: медленная сборка,
неконтролируемые зависимости, использование каждым программистом своего
подмножества языка, плохая читаемость кода, трудность написания инструментов.
Главный тезис раздела 4 этого доклада: такие проблемы не решаются добавлением
отдельных возможностей в язык — нужно смотреть на разработку ПО в целом.

В [FAQ Go](https://go.dev/doc/faq#principles) говорится, что Java и C++
требовали слишком много «бухгалтерии» и повторений, а часть программистов
в ответ уходила на динамические языки вроде Python ценой эффективности и
типобезопасности. Go задумывался как попытка соединить эффективность и
безопасность статически типизированного компилируемого языка с лёгкостью
динамического ([FAQ: Why did you create a new language?](https://go.dev/doc/faq#creating_a_new_language)).

Авторы языка — Пайк, [Кен Томпсон](../languages/people.md#thompson) и
[Роберт Гризмер](../languages/people.md#griesemer) — выбрали необычный для
создателей языков путь: самой важной характеристикой считали не набор
возможностей, а то, чего в языке **нет**.

## Идея

Язык должен быть маленьким и **ортогональным**: немного понятий, которые
свободно комбинируются без особых случаев. FAQ так и формулирует один из
принципов: методы можно определить для любого типа, структуры описывают
данные, интерфейсы — абстракцию, и ортогональность упрощает понимание того,
что происходит при их сочетании ([FAQ: guiding principles](https://go.dev/doc/faq#principles)).
Если возможность удобна, но её взаимодействие с остальным языком сложно, её
лучше не включать. FAQ объясняет, почему «вашей любимой возможности X» нет:
она может не вписываться в язык, замедлять компиляцию, усложнять дизайн
или основную модель системы ([FAQ: Why does Go not have feature X?](https://go.dev/doc/faq#Why_doesnt_Go_have_feature_X)).

Что Go сознательно не включил и чем это заменяет:

| Нет в Go | Чем заменено | Обоснование авторов |
|---|---|---|
| Наследование классов | Встраивание (embedding) и неявно реализуемые интерфейсы | [FAQ: inheritance](https://go.dev/doc/faq#inheritance), Pike 2012, §15 |
| Исключения `try`/`catch` | Ошибка — второй результат функции типа `error`; `panic`/`recover` для катастроф | [FAQ: exceptions](https://go.dev/doc/faq#exceptions), Pike 2012, §16 |
| Перегрузка функций и операторов | Разные имена | [FAQ: overloading](https://go.dev/doc/faq#overloading) |
| Аргументы по умолчанию, именованные аргументы | Структура параметров, вариативный параметр `...T` | — |
| Тернарный оператор `?:` | `if`/`else` | [FAQ: ?: operator](https://go.dev/doc/faq#Does_Go_have_a_ternary_form) |
| `while`, `do-while`, `repeat` | Один оператор `for` в трёх формах | [Spec: For statements](https://go.dev/ref/spec#For_statements) |
| `++`/`--` как выражения | Только операторы-инструкции `i++` | [FAQ: inc_dec](https://go.dev/doc/faq#inc_dec) |
| Обобщения (до Go 1.18) | `interface{}`, генерация кода; с 1.18 — параметры типов с ограничениями | [FAQ: generics](https://go.dev/doc/faq#beginning_generics) |
| Предупреждения компилятора | Только ошибки: неиспользуемая переменная или импорт не компилируются | [FAQ: unused variables](https://go.dev/doc/faq#unused_variables_and_imports) |

А что получили взамен. Пайк в разделе 10 указывает, что в Go 25 ключевых слов
(в C99 — 37, в C++11 — 84), а грамматика регулярна настолько, что программу
можно разобрать без таблицы символов и информации о типах
([список ключевых слов в спецификации](https://go.dev/ref/spec#Keywords)).
Отсюда простые инструменты: стандартная библиотека содержит лексер, парсер и
проверку типов Go. Самый заметный инструмент — `gofmt`: по словам Пайка
(§17), с самого начала проекта предполагалось, что код форматирует машина.
Поэтому у всех программ на Go один стиль, а споров о расстановке скобок нет.
Сверх этого — встроенная конкурентность (горутины и каналы), сборка мусора
и `defer` для освобождения ресурсов.

## Как это работает

Все примеры на Go в этом разделе **не запускались**: компилятора Go в
окружении автора нет. Код написан по спецификации go1.27 и проверен
по документации; ожидаемый вывод выведен из указанных разделов. Запускать —
`go run имя.go` (или `bash src/go-simplicity/run.sh`).

### Ошибка — это значение

Задача: сложить числа, записанные строками, и сообщить, в какой строке ошибка.

```go title="sum.go"
--8<-- "src/go-simplicity/sum.go"
```

```text title="Вывод (ожидаемый)"
сумма: 60
ошибка: строка 2: strconv.Atoi: parsing "x": invalid syntax
```

**Не запускалось:** вывод по документации [strconv.NumError](https://pkg.go.dev/strconv#NumError)
(формат `strconv.Atoi: parsing "x": invalid syntax`), [fmt.Errorf и `%w`](https://pkg.go.dev/fmt#Errorf),
[Go spec — Errors](https://go.dev/ref/spec#Errors).

В языке нет специального механизма для ошибок. `error` — обычный
интерфейс с одним методом `Error() string`, а функция возвращает его вторым
результатом. Проверка `if err != nil` — обычный `if`, возврат — обычный
`return`. Пайк (§16) приводит два аргумента: ошибка открытия файла — не
исключительная ситуация и не заслуживает отдельных конструкций языка, а
`try`/`catch`/`finally` переплетает несколько потоков управления. Управление в
Go-коде идёт только сверху вниз, и это видно при чтении.

Обратите внимание: компилятор **не заставляет** проверять `err`. Если написать
`n, _ := strconv.Atoi(line)`, ошибка будет молча отброшена. В
[карточке Go](../languages/go.md#errors-model) это отмечено: модель — код
ошибки, а не размеченный `Result`.

### Один цикл на всё

```go title="loops.go"
--8<-- "src/go-simplicity/loops.go:forms"
```

```text title="Вывод (ожидаемый)"
сумма квадратов: 30
шагов Коллатца для 27: 111
x: 3
0 for
1 один
```

**Не запускалось:** вывод по [Go spec — For statements](https://go.dev/ref/spec#For_statements)
(три формы: с условием, с заголовком `init; cond; post`, с `range`). Числа
пересчитаны тем же алгоритмом на Python.

Грамматика `ForStmt = "for" [ Condition | ForClause | RangeClause ] Block`
заменяет четыре оператора других языков. Для автора компилятора это значит один
узел AST и одна схема генерации кода вместо трёх или четырёх.

### Композиция вместо наследования

```go title="embed.go"
--8<-- "src/go-simplicity/embed.go:types"
```

```go title="embed.go (продолжение)"
--8<-- "src/go-simplicity/embed.go:use"
```

```text title="Вывод (ожидаемый)"
привет, пёс Шарик
привет, Шарик
Шарик — животное
```

**Не запускалось:** вывод по [Go spec — Struct types](https://go.dev/ref/spec#Struct_types)
(встроенные поля и продвижение методов), [Method sets](https://go.dev/ref/spec#Method_sets),
[Implementing an interface](https://go.dev/ref/spec#Implementing_an_interface),
[Effective Go — Embedding](https://go.dev/doc/effective_go#embedding).

Здесь сразу два решения. Первое — **структурная реализация интерфейсов**:
`Dog` и `Animal` реализуют `Namer`, потому что у них есть метод `Name() string`;
объявлять `implements` не нужно ([совместимость типов](../languages/glossary.md#typing-compatibility)).
При этом определённые типы остаются номинальными: `type Celsius float64` —
не `float64`.

Второе — **встраивание не является наследованием**. Метод `Describe` продвинут
в `Dog`, но при вызове `d.Describe()` получателем будет `d.Animal`, и внутри
него `a.Name()` вызывает `Animal.Name`, а не `Dog.Name`. Виртуального
переопределения нет — поэтому третья строка «Шарик — животное», а не
«пёс Шарик — животное». Для сравнения — тот же сюжет на Python, где
наследование реализации есть:

```python title="rich.py"
--8<-- "src/go-simplicity/rich.py"
```

```text title="Вывод"
привет, пёс Шарик
ПРИВЕТ, ПЁС ШАРИК
пёс Шарик — животное
True
```

**Проверено:** python3 3.14.7, macOS.

В Python `self.title()` внутри `Animal.describe` — виртуальный вызов, и
подкласс меняет поведение метода, который он не переписывал. Это мощный
приём, но именно он создаёт проблему «хрупкого базового класса»: чтобы понять
`describe`, надо знать все подклассы. В этом же файле — ещё три возможности,
которых в Go нет: аргумент по умолчанию `greeting="привет"`, именованный
аргумент `loud=True` и условное выражение `... if loud else ...`.

### Горутины, каналы и `defer`

```go title="concurrency.go"
--8<-- "src/go-simplicity/concurrency.go:defer"

--8<-- "src/go-simplicity/concurrency.go:chan"
```

```text title="Вывод (ожидаемый)"
тело функции
defer 2
defer 1
сумма квадратов: 55
```

**Не запускалось:** вывод по [Go spec — Defer statements](https://go.dev/ref/spec#Defer_statements)
(отложенные вызовы выполняются в обратном порядке),
[Go statements](https://go.dev/ref/spec#Go_statements),
[Channel types](https://go.dev/ref/spec#Channel_types),
[For statements with range clause](https://go.dev/ref/spec#For_range)
(цикл по каналу завершается после его закрытия).

Конкурентность встроена в язык, а не в библиотеку: оператор `go`, тип
`chan T` с направлениями `<-chan`/`chan<-` и `select`. Пайк (§13) объясняет
выбор модели CSP тем, что её можно добавить к процедурному языку почти
ортогонально, не меняя остальную модель. `defer` решает задачу `finally`
без отдельной конструкции обработки ошибок: закрытие ресурса пишется
рядом с его открытием ([освобождение ресурсов](../languages/glossary.md#resources-cleanup)).

### Обобщения, добавленные через десять лет

```go title="generics.go"
--8<-- "src/go-simplicity/generics.go:sum"
```

```text title="Вывод (ожидаемый)"
6
0.75
37
```

**Не запускалось:** вывод по [Go spec — Type parameter declarations](https://go.dev/ref/spec#Type_parameter_declarations),
[Type constraints](https://go.dev/ref/spec#Type_constraints),
[General interfaces](https://go.dev/ref/spec#General_interfaces)
(`~float64` — все типы с базовым типом `float64`). Сумма `36.6 + 0.4` в
`float64` равна ровно `37` — проверено на Python.

Go 1.0 вышел в 2012 году без обобщений; параметры типов появились в
[Go 1.18](https://go.dev/doc/go1.18) в марте 2022-го. FAQ объясняет задержку:
обобщения удобны, но усложняют систему типов и среду выполнения, и понадобилось
время, чтобы найти дизайн, польза которого соразмерна сложности
([FAQ: Why was Go initially released without generic types?](https://go.dev/doc/faq#beginning_generics)).
Итоговый вариант ограничен: у методов не может быть собственных параметров
типов, и FAQ прямо говорит, что их не планируют добавлять, потому что неясно,
как совместить их с динамической проверкой интерфейсов
([FAQ: generic methods](https://go.dev/doc/faq#generic_methods)). Здесь видно
взаимодействие возможностей: структурные интерфейсы и обобщённые методы плохо
сочетаются, и язык выбрал первые.

## Цена

**Многословие обработки ошибок.** Это главная претензия к Go. В записи блога
[«[ On | No ] syntactic support for error handling»](https://go.dev/blog/error-syntax)
(Гризмер, 2025) команда Go признаёт: жалобы на многословие обработки ошибок
годами занимают первое место в опросах пользователей. В той же записи
перечислены попытки упростить синтаксис: черновик `check`/`handle` (2018),
встроенная функция `try` (2019, около 900 комментариев в обсуждении), оператор
`?` по образцу Rust (2024). Ни одна не набрала консенсуса, и команда решила
пока не менять синтаксис. Аргумент «за» статус-кво: явный поток управления
виден в коде; аргумент «против»: в функции из десяти строк шесть уходят на
`if err != nil { return err }`.

**Шаблонный код.** Без аргументов по умолчанию появляются паттерны вроде
«функциональных опций» и структур конфигурации. Без перегрузки —
`strconv.Atoi`, `strconv.ParseInt`, `strconv.ParseFloat` вместо одного имени.
Без условного выражения — четыре строки `if`/`else` вместо одной. Код длиннее,
и авторы это признают: в §16 Пайк пишет, что код с явными ошибками может быть
длиннее, но это окупается ясностью.

**Долгий спор об обобщениях.** Десять лет между Go 1.0 и Go 1.18 библиотеки
обходились `interface{}` с проверкой типов во время выполнения или генерацией
кода. Контейнеры и алгоритмы общего вида писали по нескольку раз. После
добавления параметров типов язык стал сложнее: появились наборы типов в
интерфейсах (`~int | ~float64`), вывод аргументов типов, новые правила
идентичности. «Бедность» не абсолютна — это выбор момента и формы, и он
затронул уже написанный код.

**Нет гарантий проверки.** Многие ошибки, которые язык мог бы исключить
статически, остаются: забытая проверка `err`, разыменование `nil`-указателя,
гонки данных между горутинами (для них есть детектор гонок в инструментах,
а не в системе типов). Сам Пайк в заключении доклада 2012 года называет
неудачные места: слишком много форм объявления переменных и путаница с
`nil`-значением внутри не-`nil` интерфейса.

**Цена для автора языка — эволюция.** [Обещание совместимости Go 1](https://go.dev/doc/go1compat)
делает каждое добавление почти необратимым. FAQ отвечает на вопрос «примете ли
вы моё изменение языка?» тем, что принимают очень немногие
([FAQ: language changes](https://go.dev/doc/faq#language_changes)).
Минимализм здесь — ещё и способ оставить себе пространство для будущих решений.

## Сравнение

Та же задача, что в `sum.go`, в двух «богатых» языках.

```python title="sum.py"
--8<-- "src/go-simplicity/sum.py"
```

```text title="Вывод"
сумма: 60
ошибка: invalid literal for int() with base 10: 'x'
```

**Проверено:** python3 3.14.7, macOS.

```rust title="sum.rs"
--8<-- "src/go-simplicity/sum.rs"
```

```text title="Вывод"
сумма: 60
ошибка: invalid digit found in string
```

**Проверено:** rustc 1.98.1 (`--edition 2021`), macOS.

| | Go | Python | Rust |
|---|---|---|---|
| Где видна ошибка | В сигнатуре `(int, error)` и в каждом `if err != nil` | Нигде: исключение может вылететь из любой строки | В типе `Result<i64, ParseIntError>`; `?` — явная точка выхода |
| Можно ли забыть ошибку | Да: `n, _ := ...` компилируется | Да: исключение уйдёт выше по стеку | Компилятор предупредит: `Result` помечен `#[must_use]`; отбросить можно только явно |
| Сколько механизмов нужно знать | `if`, `return`, интерфейс `error` | `try`/`except`, иерархия исключений | `Result`, `?`, итераторы, `collect` в `Result` |
| Размер тела `total` | 9 строк | 1 строка | 5 строк |

Python и Rust решают задачу короче, но за счёт разных механизмов, которые
читатель должен знать: раскрутка стека исключениями или комбинация
итераторов, трейта `FromIterator` для `Result` и оператора `?`. В Go тот же
код читается человеком, знающим только `for`, `if` и `return`. Какой из
вариантов лучше — вопрос о том, чего стоит внимание читателя и чего стоит
его ошибка; Rust, например, делает забытую ошибку предупреждением компилятора,
а Go оставляет её на совести программиста.

## Что взять в свой язык

**Маленькую грамматику дешевле реализовать и выучить.** Каждое правило в `.g4`
тянет за собой узел AST, проверку в семантическом анализаторе, генерацию кода,
тесты и сообщения об ошибках. Один `for` в трёх формах вместо `while`, `until`
и `do-while` — это одна ветка в генераторе. Но требования практикума просят
отдельные `while` и `until` ([требование 7.2](../labs/index.md#trebovaniya)):
их можно реализовать как синтаксический сахар, переписывая в общий узел цикла
ещё при построении AST. Так вы получаете разнообразие для пользователя и
минимализм для компилятора.

**Возможности взаимодействуют.** Полезно нарисовать матрицу «возможность ×
возможность» и заполнить клетки вопросами. Перегрузка × неявные
преобразования: какую функцию выбрать для `f(1)`, если есть `f(float)` и
`f(long)`? Перегрузка × аргументы по умолчанию: `f(int)` и `f(int, int = 0)`
неразличимы при вызове `f(1)`. Множественное присваивание × передача по
ссылке: что значит `a, b = b, a`, если `a` и `b` — псевдонимы? Именно такие
клетки заставили Go отказаться от перегрузки
([FAQ: overloading](https://go.dev/doc/faq#overloading)) и отложить обобщения.

**Варианты практикума — это выбор возможностей.** В
[свойствах языка](../labs/index.md#svoystva) вам выпадают перегрузка
подпрограмм (свойство 7), способ передачи параметров (8), `switch` (6),
множественное присваивание (3). Если перегрузка «отсутствует», это не
недоработка, а решение в духе Go: таблица символов хранит одно имя —
одну функцию, и сообщения об ошибках проще. Если «присутствует», заранее
определите правило разрешения и ошибку неоднозначности. Сопоставление
вариантов с реальными языками — в [таблице соответствий](../languages/lab-mapping.md#variants-7).

**Ошибки лучше, чем предупреждения.** Решение Go не выдавать предупреждений
([FAQ](https://go.dev/doc/faq#unused_variables_and_imports)) легко повторить:
семантический анализатор, который отклоняет неиспользуемую переменную, проще
тестировать, чем анализатор с уровнями строгости.

**Грамматика без контекста помогает инструментам.** Go разбирается без таблицы
символов. В C `a * b;` — это умножение или объявление указателя в зависимости
от того, объявлен ли `a` как тип. Если ваш язык разбирается без обратной связи
от семантического анализа, ANTLR-грамматика останется чистой, а форматтер или
подсветку можно написать поверх того же парсера (см. лекцию
[«Критерии оценки языков программирования»](../lectures/html/20-kriterii-ocenki-yazykov-programmirovaniya.html)
о простоте и ортогональности).

## Упражнение

1. Предскажите вывод `embed.go`, если в `Dog` дописать метод
   `func (d Dog) Describe() string { return d.Name() + " — собака" }`.
   Что изменится в третьей строке и почему теперь поведение совпадёт с Python?

    ??? question "Ответ"
        Третья строка станет `пёс Шарик — собака`: `d.Describe()` теперь находит
        метод `Dog.Describe` на глубине 0, он скрывает продвинутый `Animal.Describe`
        ([Selectors](https://go.dev/ref/spec#Selectors)), а внутри `d.Name()`
        вызывает `Dog.Name`. Совпадение с Python только внешнее: в Go это
        статический выбор метода по типу `Dog`, а не виртуальный вызов из базового
        класса — `d.Animal.Describe()` по-прежнему даст `Шарик — животное`.

2. Составьте для своего варианта практикума матрицу взаимодействия 4–5
   возможностей (например, перегрузка, неявные преобразования, передача по
   ссылке, вложенные подпрограммы, множественное присваивание). Для каждой
   непустой клетки запишите пример программы, в которой взаимодействие
   проявляется, и правило, которое примет ваш компилятор. Какую возможность
   вы бы убрали, если бы вариант это разрешал?
