# Rust: владение и заимствование

*Безопасность памяти без сборщика мусора — это статический анализ в компиляторе, который следит, кто владеет значением и кто на него ссылается.*

## Проблема

Программа, которая выделяет память в куче, должна когда-нибудь её вернуть.
Исторически сложились два ответа.

**Ручное освобождение** (C: `malloc`/`free`). Программист сам решает, когда
память больше не нужна. Компилятор этому решению не мешает и его не проверяет.
Отсюда классические ошибки: использование после освобождения (use-after-free),
двойное `free`, утечки, висячие указатели на локальные переменные уже
завершившейся функции. Язык C проектировался как близкий к машине язык
системного программирования ([Ritchie, HOPL II](../languages/sources.md#hopl-c)),
и проверка времени жизни указателей в эту модель не входила.

**Автоматическое освобождение во время выполнения.** Трассирующий сборщик
мусора (Java, C#, Go, Lisp) периодически находит недостижимые объекты;
подсчёт ссылок (CPython, Swift, `std::shared_ptr` в C++) освобождает объект,
когда исчезает последняя ссылка. Ошибки use-after-free исчезают, но появляется
среда выполнения: паузы или накладные расходы сборщика, счётчики в каждом
объекте, недетерминированный момент освобождения (для GC), утечки через циклы
ссылок (для подсчёта ссылок).

Есть и промежуточный путь — **RAII** (Resource Acquisition Is Initialization) в
C++: ресурс принадлежит объекту, деструктор освобождает его при выходе объекта
из области видимости. `std::unique_ptr` выражает единственного владельца,
`std::move` передаёт владение. Но C++ не проверяет, что после `std::move`
старый объект больше не используют, и не проверяет, что сырой указатель или
ссылка не пережили владельца ([Stroustrup, HOPL II](../languages/sources.md#hopl-cpp)).

Rust, начатый [Грейдоном Хоаром](../languages/people.md#graydon-hoare),
берёт RAII из C++ и добавляет то, чего там не хватало: компилятор доказывает,
что каждое обращение к памяти происходит, пока её владелец жив, и что
изменяемый доступ не пересекается с другими ссылками. Никакой проверки во
время выполнения для этого не нужно.

## Идея

Три правила из главы 4 книги
[The Rust Programming Language](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html):
у каждого значения есть **владелец** (owner) — переменная, поле или элемент
коллекции; владелец в каждый момент ровно один; когда владелец выходит из
области видимости, значение уничтожается (вызывается `Drop`). Присваивание или
передача значения в функцию **перемещает** (move) владение: старое имя
становится недействительным. Исключение — типы с признаком `Copy` (целые
числа, `bool`, `&T`), они копируются побитово.

Чтобы не передавать владение туда и обратно, значение можно **заимствовать**
(borrowing) — взять ссылку. Ссылки бывают двух видов:

- `&T` — разделяемая (shared): читать можно, таких ссылок сколько угодно;
- `&mut T` — исключительная (exclusive): можно менять, но пока она жива,
  никаких других ссылок на то же значение быть не может.

В книге это сформулировано так: «At any given time, you can have either one
mutable reference or any number of immutable references»
([ch. 4.2](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html)).
Короткое название — *aliasing XOR mutability*: псевдонимы или изменяемость,
но не одновременно. И второе правило: ссылка не может жить дольше значения.
Отрезок программы, на котором ссылка обязана оставаться валидной, называется
**временем жизни** (lifetime); внутри функции компилятор выводит его сам, а на
границе функций его иногда приходится писать явно: `'a`.

Часть компилятора, которая проверяет эти правила, называется **borrow
checker**. Это обычный статический анализ потока данных над промежуточным
представлением (MIR в rustc): для каждой точки программы он знает, какие
переменные инициализированы, какие перемещены и какие заимствования активны.
Начиная с [non-lexical lifetimes (RFC 2094)](https://rust-lang.github.io/rfcs/2094-nll.html)
заимствование заканчивается не в конце блока, а после последнего использования
ссылки.

Отдельно от этого — изменяемость имён. Переменная без `mut` неизменяема
([изменяемость связываний](../languages/glossary.md#bindings-mutation)); `let mut`
разрешает менять значение и брать `&mut`. Это делает запись в данные видимой в
тексте программы.

## Как это работает

Все примеры собраны командой `rustc --edition 2024 файл.rs`; скрипт
`src/rust-ownership/run.sh` воспроизводит их целиком. Из диагностик
компилятора оставлены ключевые строки; подсказки `note:`/`help:` опущены
(кроме E0106, где подсказка и есть суть).

### Перемещение и использование после перемещения

```rust title="move_error.rs"
--8<-- "src/rust-ownership/move_error.rs"
```

```text title="Вывод"
error[E0382]: borrow of moved value: `s`
  --> move_error.rs:10:16
   |
 7 |     let s = String::from("привет");
   |         - move occurs because `s` has type `String`, which does not implement the `Copy` trait
 8 |     let n = consume(s); // владение строкой перемещено в параметр consume
   |                     - value moved here
 9 |     println!("{n}");
10 |     println!("{s}"); // ошибка: s больше ничем не владеет
   |                ^ value borrowed here after move
```

**Проверено:** rustc 1.98.1, macOS.

`String` — это указатель на буфер в куче, длина и ёмкость. Если бы после
`consume(s)` обе переменные считались владельцами, буфер освободили бы дважды:
в конце `consume` и в конце `main`. Rust решает это так: после перемещения `s`
для компилятора — неинициализированная переменная. Это та же проверка, что
«переменная использована до присваивания», только состояние «перемещено»
возникает не только при объявлении. Дальше компилятор предлагает два выхода:
принимать `&String` (заимствовать) или явно вызвать `clone()`.

### Разделяемое и исключительное заимствование

```rust title="borrow_conflict.rs"
--8<-- "src/rust-ownership/borrow_conflict.rs"
```

```text title="Вывод"
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
 --> borrow_conflict.rs:6:5
  |
5 |     let first = &v[0]; // разделяемое заимствование v
  |                  - immutable borrow occurs here
6 |     v.push(4); // push требует &mut v, а first ещё жив
  |     ^^^^^^^^^ mutable borrow occurs here
7 |     println!("{first}");
  |                ----- immutable borrow later used here
```

**Проверено:** rustc 1.98.1, macOS.

Здесь нет ни одного `free`, но ошибка та же, что в C. `push` может не
поместиться в текущий буфер, выделить новый и освободить старый, а `first`
указывает в старый. В C++ это «инвалидация итераторов» `std::vector`; она
описана в документации, но не проверяется. Правило «один писатель или много
читателей» запрещает весь этот класс ошибок сразу. Причём компилятору не нужно
знать, что делает `push`: достаточно сигнатуры `fn push(&mut self, value: T)`.

Если перенести `println!("{first}")` выше `v.push(4)`, программа
скомпилируется: заимствование `first` закончится после последнего
использования.

### Функция, принимающая `&mut`

```rust title="mut_ref.rs"
--8<-- "src/rust-ownership/mut_ref.rs"
```

```text title="Вывод"
[1, 7, 7] sum=15 len=3
```

**Проверено:** rustc 1.98.1, macOS.

`&mut v` на месте вызова — явный признак того, что функция изменит аргумент.
Параметры по-прежнему передаются по значению
([способы передачи параметров](../languages/glossary.md#subprograms-parameter-passing)),
просто значением здесь является ссылка. Исключительное заимствование живёт до
конца вызова, после этого можно снова брать сколько угодно `&v`.

### Время жизни: висячая ссылка

```rust title="dangling.rs"
--8<-- "src/rust-ownership/dangling.rs"
```

```text title="Вывод"
error[E0597]: `s` does not live long enough
 --> dangling.rs:6:13
  |
5 |         let s = String::from("временная");
  |             - binding `s` declared here
6 |         r = &s; // заимствуем s ...
  |             ^^ borrowed value does not live long enough
7 |     } // ... но s уничтожается здесь
  |     - `s` dropped here while still borrowed
8 |     println!("{r}"); // висячая ссылка — компилятор не пропустит
  |                - borrow later used here
```

**Проверено:** rustc 1.98.1, macOS.

Внутри функции времена жизни выводятся. На границе функции компилятор смотрит
только на сигнатуру, а не на тело. Поэтому если функция возвращает ссылку и
принимает две, нужно сказать, от какой из них зависит результат:

```rust title="no_lifetime.rs"
--8<-- "src/rust-ownership/no_lifetime.rs"
```

```text title="Вывод"
error[E0106]: missing lifetime specifier
 --> no_lifetime.rs:3:33
  |
3 | fn longest(a: &str, b: &str) -> &str {
  |               ----     ----     ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but the signature does not say whether it is borrowed from `a` or `b`
```

**Проверено:** rustc 1.98.1, macOS.

Исправленная версия с параметром `'a` означает «результат живёт не дольше, чем
оба аргумента»:

```rust title="lifetimes.rs"
--8<-- "src/rust-ownership/lifetimes.rs"
```

```text title="Вывод"
длинная строка
```

**Проверено:** rustc 1.98.1, macOS.

Аннотация `'a` ничего не меняет во время выполнения. Это часть типа, которая
позволяет проверять функции по отдельности: вызывающая сторона видит
контракт, не читая тело `longest`. В простых случаях (одна входная ссылка,
метод с `&self`) аннотации подставляются по правилам
[lifetime elision](https://doc.rust-lang.org/reference/lifetime-elision.html).

### `Drop` и порядок уничтожения

```rust title="drop_order.rs"
--8<-- "src/rust-ownership/drop_order.rs"
```

```text title="Вывод"
конец внутреннего блока
drop c
take получила b
drop b
конец main
drop d
drop a
```

**Проверено:** rustc 1.98.1, macOS.

Это [освобождение ресурсов в стиле RAII](../languages/glossary.md#resources-cleanup):
деструктор вызывается при выходе владельца из области видимости. Переменные
уничтожаются в порядке, обратном объявлению
([Rust Reference, Destructors](https://doc.rust-lang.org/reference/destructors.html)).
Перемещение переносит и обязанность вызвать деструктор: `b` уничтожена в
конце `take`, а не в `main`. Тот же механизм закрывает файлы, отпускает
мьютексы и сокеты, так что отдельный `finally` или `defer` не нужен.

### `Rc<RefCell<T>>`: когда статических правил мало

Не все структуры данных укладываются в «один владелец»: графы, двусвязные
списки, общее состояние нескольких частей программы. Стандартная библиотека
даёт два механизма. `Rc<T>` — разделяемое владение с подсчётом ссылок.
`RefCell<T>` — внутренняя изменяемость (interior mutability): те же правила
заимствования, но проверяемые во время выполнения
([ch. 15.5](https://doc.rust-lang.org/book/ch15-05-interior-mutability.html)).

```rust title="rc_refcell.rs"
--8<-- "src/rust-ownership/rc_refcell.rs"
```

```text title="Вывод"
владельцев: 2
[1, 2, 3, 4]
try_borrow_mut без конфликтов: true
try_borrow_mut при живом guard: Some(BorrowMutError)

thread 'main' (4513464) panicked at rc_refcell.rs:19:25:
RefCell already borrowed
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

Код выхода процесса — 101; номер потока в строке паники меняется от запуска к
запуску.

**Проверено:** rustc 1.98.1, macOS.

Программа компилируется: компилятор видит только `&RefCell`, а разделяемые
ссылки не конфликтуют. Нарушение «одного писателя» обнаруживается в момент
выполнения: `try_borrow_mut` возвращает `Err(BorrowMutError)`, а `borrow_mut`
паникует. Это честный обмен: гибкость в обмен на проверку во время выполнения
и возможную панику. Кроме того, `Rc` возвращает известную проблему подсчёта
ссылок — циклы, которые никогда не освободятся; для них есть `Weak`
([ch. 15.6](https://doc.rust-lang.org/book/ch15-06-reference-cycles.html)).

## Цена

**Порог входа и «борьба с borrow checker».** Правила консервативны: анализ
отвергает часть корректных программ. Типичные случаи — одновременное
изменяемое заимствование двух разных элементов одного массива (решается
`split_at_mut`), методы, которым нужен `&mut self` целиком, хотя меняется одно
поле, циклические структуры. Над более точным анализатором
([Polonius](https://rust-lang.github.io/polonius/)) работа ведётся отдельно,
то есть граница «что принимается» со временем сдвигается.

**Архитектура подстраивается под владение.** Графы объектов, где «все
ссылаются на всех», в Rust записывают через индексы в вектор, `Rc<RefCell<…>>`
или арены. Это не всегда плохо: владение становится явной частью дизайна. Но
перенос кода с языка со сборщиком мусора часто означает переписывание, а не
перевод.

**Сигнатуры становятся сложнее.** Времена жизни, обобщения и ограничения
трейтов вместе дают длинные заголовки функций. В карточке
[Rust](../languages/rust.md) это отмечено как цена читаемости.

**Гарантии не абсолютны.** В безопасном Rust нет use-after-free и гонок данных,
но утечки памяти безопасными не считаются: `std::mem::forget` не помечен как
`unsafe`, а цикл из `Rc` тоже течёт. Код внутри `unsafe` (реализация `Vec`,
`RefCell`, FFI) проверяет программист. Обоснование того, что безопасные
абстракции поверх `unsafe` действительно безопасны, — отдельная исследовательская
задача: её формализует проект
[RustBelt](https://doi.org/10.1145/3158154) (Jung и др., POPL 2018).

**Время компиляции.** Borrow checker — один из проходов, которых нет у
компиляторов C. Но заметная часть времени сборки Rust приходится на
мономорфизацию и LLVM, так что считать весь его вклад ценой владения нельзя.

## Сравнение

| | Кто освобождает | Use-after-free | Одновременная запись и чтение по псевдонимам | Когда выполняется очистка |
|---|---|---|---|---|
| C | программист, `free` | возможен, UB | разрешено | когда вызван `free` |
| C++ | деструктор (`unique_ptr`) | возможен через сырые указатели и после `move` | разрешено | при выходе из области |
| Java, Python | GC / подсчёт ссылок | невозможен | разрешено | GC — когда решит сборщик; CPython — обычно сразу |
| Swift | подсчёт ссылок (ARC) | невозможен для сильных ссылок | разрешено для классов | когда счётчик стал 0 |
| Rust | владелец, `Drop` | запрещён статически (вне `unsafe`) | запрещено статически | при выходе владельца из области |

**C.** Компилятор принимает use-after-free без ошибок:

```c title="use_after_free.c"
--8<-- "src/rust-ownership/use_after_free.c"
```

`clang -Wall` не выдал предупреждений, программа завершилась с кодом 0 и
напечатала один мусорный байт и перевод строки (при двух запусках — разные
байты). Это неопределённое поведение: результат зависит от распределителя
памяти. Предупреждение появилось только у отдельного статического анализатора:

```text title="Вывод clang --analyze"
use_after_free.c:10:5: warning: Use of memory after it is freed [unix.Malloc]
   10 |     printf("%s\n", s); /* use-after-free: неопределённое поведение */
      |     ^~~~~~~~~~~~~~~~~
1 warning generated.
```

**Проверено:** Apple clang 17.0.0, macOS.

**C++.** `unique_ptr` и `std::move` дают ту же модель владения, что Rust, но
без проверки:

```cpp title="unique_ptr.cpp"
--8<-- "src/rust-ownership/unique_ptr.cpp"
```

```text title="Вывод"
5
p пуст после move
```

**Проверено:** Apple clang 17.0.0 (`clang++ -std=c++17`), macOS.

После `std::move(p)` объект `p` остаётся живым, но пустым, и строка `*p`
скомпилировалась бы. Внешние линтеры (например, проверка
`bugprone-use-after-move` в clang-tidy) ловят часть таких случаев, но язык их
не запрещает. Главное отличие не в синтаксисе владения, а в том, что в Rust
перемещённая переменная для компилятора перестаёт существовать.

**Java и Python.** Сборщик мусора (в CPython — подсчёт ссылок и
[сборщик циклов](https://docs.python.org/3/reference/datamodel.html))
решает проблему освобождения памяти, но не проблему псевдонимов:
изменить коллекцию во время обхода её итератором язык не запрещает. В лучшем
случае ошибку покажет проверка во время выполнения: `ConcurrentModificationException`
у коллекций Java, `RuntimeError` у словарей и множеств Python. У списков Python
такой проверки нет вовсе: обход просто пропускает или повторяет элементы. Для файлов и сокетов
нужны отдельные конструкции — `try`-with-resources и `with`.

**Swift.** [ARC](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/automaticreferencecounting/)
вставляет инкременты и декременты счётчика на этапе компиляции. Это ближе к
`Rc` в Rust, только используется по умолчанию для всех классов. Циклы нужно
разрывать вручную ссылками `weak`/`unowned`.

## Что взять в свой язык

**Что нужно отслеживать семантическому анализатору.** Для владения и
перемещений:

- для каждой переменной и точки программы — состояние
  «инициализирована / перемещена / может быть перемещена» (последнее — после
  `if`, где перемещение было только в одной ветке);
- это задача анализа потока данных на графе потока управления, та же, что
  «definite assignment» в Java и C#. Если у вас уже есть проверка «переменная
  использована до присваивания», перемещение добавляется как ещё одна
  операция «сделать неинициализированной».

Для заимствований нужно больше:

- для каждой ссылки — область (множество точек программы), где она жива;
- для каждой точки — множество активных заимствований с видом (`&` или `&mut`)
  и путём (`v`, `v.field`, `v[_]`);
- проверка конфликтов: любое обращение к пути сравнивается с активными
  заимствованиями пересекающихся путей;
- на границе функций — параметры времени жизни в типах, их вывод и
  подстановка, правила подтипизации (`'long: 'short`).

**Почему это трудно в учебном компиляторе.** Анализ требует CFG и анализа
живучести; на AST (как обычно устроен семантический анализ на ANTLR-посетителях)
его корректно не сделать, особенно при циклах и `break`. Времена жизни
пронизывают систему типов: обобщения, структуры со ссылками, замыкания.
Диагностика должна объяснять, *где* начался конфликт, иначе язык невозможно
использовать. Для курсовой работы полноценный borrow checker — задача заметно
больше остального компилятора.

**Упрощённые варианты, которые реально сделать:**

1. **Неизменяемость по умолчанию.** `let` против `let mut` (или `val`/`var`) —
   одно поле в таблице символов и одна проверка при присваивании. Это не
   владение, но убирает часть случайных изменений.
2. **Аффинные (move-only) типы без ссылок.** Значения некоторого вида (файл,
   буфер) можно использовать не больше одного раза; после передачи переменная
   недоступна. Нужен только анализ «перемещено/нет» — ссылок и времён жизни
   нет. Линейный вариант (использовать ровно один раз) добавляет проверку, что
   значение не забыли: ошибка, если на выходе из области переменная всё ещё
   владеет ресурсом.
3. **Второй класс ссылок.** Разрешить `&` только в параметрах функций и
   запретить возвращать ссылки и хранить их в структурах. Тогда ссылка
   гарантированно не переживёт вызов, и времена жизни не нужны. Примерно так
   устроены `inout`-параметры в Swift.
4. **Детерминированная очистка.** Даже со сборщиком мусора в целевой
   платформе (JVM, CIL, CPython) можно генерировать вызов деструктора при
   выходе из блока — как `try/finally`, в который компилятор оборачивает
   блок. Для LLVM и WASM без GC это и есть основной способ освобождения
   памяти.

Для генерации кода владение почти бесплатно: перемещение — это копирование
нескольких слов, `Drop` — вызов функции в точках выхода из области (включая
ранние `return` и `break`). Вся сложность — в семантическом анализе. Об
устройстве этапов анализа см. лекцию
[«Семантический анализатор»](../lectures/html/07-semanticheskiy-analizator.html).

## Упражнение

1. Предскажите, скомпилируется ли программа, и если нет — с каким кодом ошибки:

   ```rust
   fn main() {
       let mut s = String::from("a");
       let r1 = &s;
       let r2 = &s;
       println!("{r1} {r2}");
       let w = &mut s;
       w.push('b');
       println!("{s}");
   }
   ```

   ??? question "Ответ"
       Скомпилируется и напечатает `a a`, затем `ab`. Заимствования `r1` и `r2`
       заканчиваются после первого `println!` (NLL), поэтому `&mut s` на
       следующей строке законно. `w` последний раз используется в `w.push('b')`,
       после чего `s` снова можно читать. Если добавить `println!("{r1}")` в
       конец, получится E0502.

2. Добавьте в язык своего курсового проекта модификатор `own` для
   типа-ресурса (например, `own File`). Опишите в терминах атрибутов таблицы
   символов и обхода CFG, как обнаружить: (а) использование после передачи в
   функцию; (б) ресурс, не переданный и не закрытый к концу блока. Какие
   конструкции вашего языка (циклы, ранний `return`, `break`) усложняют
   анализ и почему?
