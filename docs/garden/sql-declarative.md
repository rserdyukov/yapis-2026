# SQL: декларативность

*Запрос задаёт свойства результата, а не шаги вычисления: порядок обхода, соединений и выбор индексов остаются за СУБД.*

## Проблема

До реляционной модели программа, работавшая с базой данных, знала, как данные
лежат физически: в каком порядке хранятся записи, какие индексы есть,
по каким указателям переходить от одной записи к другой. Эдгар Кодд в статье
1970 года ([codd-1970](../languages/sources.md#codd-1970)) начинает именно с этого.
Он перечисляет три вида зависимости прикладных программ от представления:
от порядка записей (ordering dependence), от индексов (indexing dependence) и
от путей доступа (access path dependence). Стоит поменять хранение, и
программы перестают работать или начинают отвечать неправильно.

Кодд предложил отделить логическую модель от физической. Данные описываются
как отношения (relations), то есть множества кортежей над доменами. Запрос
выражается операциями над отношениями и ничего не говорит о том, как они
хранятся. Через четыре года Дональд Чемберлин и Рэймонд Бойс описали SEQUEL
([sequel-1974](../languages/sources.md#sequel-1974)) — язык запросов с
английскими ключевыми словами, из которого вырос SQL. Их общая мысль:
пользователь формулирует, *что* он хочет получить, и не описывает навигацию
по записям.

Для автора языка это та же задача, что стоит перед любым компилятором:
отделить смысл программы от стратегии её исполнения. В SQL этот разрыв
особенно широк. Программа задаёт ограничения на результат, а алгоритм
строится во время выполнения по статистике данных.

## Идея

Запрос SQL описывает результирующее множество строк: из каких таблиц они
берутся (`FROM`), какому условию удовлетворяют (`WHERE`, `ON`), как
группируются и агрегируются (`GROUP BY`, `HAVING`), какие столбцы возвращаются
(`SELECT`). Порядок, в котором эти предложения записаны, не совпадает с порядком
вычисления. Стандарт определяет только смысл запроса. Выбор между
последовательным сканированием и индексом, вложенными циклами и хеш-соединением,
а также порядок соединения таблиц принимает оптимизатор (query planner).

В карточке языка это отражено как парадигма
[`declarative`](../languages/glossary.md#paradigm-supported), а стратегия
вычисления — как [`n/a`](../languages/glossary.md#evaluation-strategy).
«Строгий» и «нестрогий» здесь не подходят: подвыражения могут вычисляться в
любом порядке или не вычисляться вовсе, и порядок гарантирует только `CASE`.
Карточка [SQL](../languages/sql.md) описывает стандарт ISO/IEC 9075. Все
примеры ниже запускались в SQLite, и каждое место, где поведение
специфично для SQLite, отмечено отдельно.

Все примеры используют одну небольшую схему: отделы, сотрудники с
необязательными отделом и руководителем и граф из трёх рёбер.

```sql title="data.sql"
--8<-- "src/sql-declarative/data.sql"
```

## Разбор примеров

Все SQL-файлы запускаются одинаково: `cat data.sql файл.sql | sqlite3 -batch :memory:`
(опции вывода см. в `run.sh`).

### 1. Один запрос, два плана

Возьмём один и тот же запрос — имена сотрудников отдела `runtime` — и попросим
SQLite показать план до создания индекса и после.

```sql title="plan.sql (до индекса)"
--8<-- "src/sql-declarative/plan.sql:before"
```

```sql title="plan.sql (после индекса)"
--8<-- "src/sql-declarative/plan.sql:after"
```

```sql title="plan.sql (сам результат)"
--8<-- "src/sql-declarative/plan.sql:result"
```

```text title="Вывод"
QUERY PLAN
|--SCAN e
`--SEARCH d USING INTEGER PRIMARY KEY (rowid=?)
QUERY PLAN
|--SCAN d
`--SEARCH e USING INDEX emp_dept (dept_id=?)
dan
eve
```

**Проверено:** SQLite 3.51.0, macOS.

Текст запроса не менялся, а план поменялся. Без индекса SQLite перебирает
всех сотрудников (`SCAN e`) и для каждого находит отдел по первичному ключу.
После `CREATE INDEX` внешний цикл идёт уже по отделам (`SCAN d`), а
сотрудники нужного отдела ищутся по индексу. Порядок соединения
переставлен, и программист в этом не участвовал. Результат остаётся тем же:
`dan`, `eve`.

!!! note "Специфика SQLite"
    `EXPLAIN QUERY PLAN` и формат его вывода — расширение SQLite. Документация
    [предупреждает](https://www.sqlite.org/eqp.html), что формат менялся между
    выпусками и полагаться на него нельзя. В PostgreSQL та же идея реализована
    командой [`EXPLAIN`](https://www.postgresql.org/docs/current/using-explain.html)
    с другим форматом. В стандарте SQL команды показа плана нет: план не входит
    в смысл запроса.

### 2. Соединения вместо циклов, группы вместо аккумуляторов

В императивном коде «сумма зарплат по отделам» записывается как вложенный
цикл с аккумуляторами. В SQL вместо этого пишут соединение (`JOIN`), разбиение
на группы (`GROUP BY`) и фильтр по группам (`HAVING`). Оконные функции
(window functions) отвечают на другой вопрос: они вычисляют значение по группе
*для каждой строки* и не сворачивают группу в одну строку.

```sql title="aggregate.sql"
--8<-- "src/sql-declarative/aggregate.sql"
```

```text title="Вывод"
title      n  total  top
---------  -  -----  ---
compilers  3  700    300
runtime    2  500    250
name  dept_id  salary  rnk  dept_total
----  -------  ------  ---  ----------
ada   1        300     1    700
bob   1        200     2    700
lee   1        200     2    700
dan   2        250     1    500
eve   2        250     1    500
```

**Проверено:** SQLite 3.51.0, macOS (`sqlite3 -header -column`).

Отдела `docs` в результате нет, потому что `JOIN` не нашёл для него строк.
Сотрудницы `kim` тоже нет: её `dept_id` равен `NULL`, а условие `d.id = e.dept_id`
для неё не истинно. У `bob` и `lee` одинаковый ранг 2. Ранг описан как свойство
множества строк («сколько строк строго выше плюс один»), а не как номер
итерации. Если бы порядок был важен, пришлось бы добавить в `ORDER BY` окна
второй ключ.

Оконные функции появились в SQLite в версии 3.25.0
([история](https://www.sqlite.org/windowfunctions.html)). Разработчики
SQLite ориентировались на документацию PostgreSQL, так что синтаксис
`OVER (PARTITION BY … ORDER BY …)` здесь стандартный.

### 3. Рекурсивный CTE как неподвижная точка

Одними соединениями не выразить транзитивное замыкание: число шагов заранее
неизвестно. `WITH RECURSIVE` добавляет в язык итерацию, но записывается она
как уравнение: `reach` — это рёбра плюс рёбра, продолжающие уже найденные пути.
Сравните с программой Datalog из
[различающего примера](../concepts/examples/index.md#datalog). Правила там те
же, и граф тот же: `a → b`, `b → a`, `b → c`.

```sql title="reach.sql"
--8<-- "src/sql-declarative/reach.sql:reach"
```

```text title="Вывод"
x  y
-  -
a  a
a  b
a  c
b  a
b  b
b  c
```

**Проверено:** SQLite 3.51.0, macOS.

Получилось то же множество из шести пар, что рассчитано для Datalog. Пары
`(c, c)` нет, потому что из `c` не выходит ни одного ребра. В этом смысле
запрос вычисляет наименьшую неподвижную точку
([`least_fixed_point`](../languages/glossary.md#computation-rule-semantics)).
Цикл `a → b → a` не мешает завершению, так как `UNION` отбрасывает уже
известные строки и приращение в какой-то момент становится пустым. Если
заменить `UNION` на `UNION ALL`, поведение изменится:

```sql title="reach.sql (UNION ALL)"
--8<-- "src/sql-declarative/reach.sql:union-all"
```

```text title="Вывод"
rows  distinct_pairs
----  --------------
1000  6
```

**Проверено:** SQLite 3.51.0, macOS.

Различных пар по-прежнему шесть, но строк столько, сколько разрешил `LIMIT`.
Без него запрос не завершится. `LIMIT` внутри рекурсивной части — расширение
SQLite. В PostgreSQL для отладки советуют ставить `LIMIT` во внешнем запросе,
но предупреждают, что это работает не всегда. Разница между множеством и мультимножеством
([кратность](../languages/glossary.md#data-collection-multiplicity)) решает,
завершится ли вычисление вообще.

!!! note "Стандарт и SQLite"
    [SQLite](https://www.sqlite.org/lang_with.html) реализует рекурсию через
    очередь строк: из очереди извлекается одна строка, и рекурсивная часть
    выполняется так, будто в таблице только она. С `UNION` строка попадает в
    очередь, только если такой ещё не было. Там же сказано, что `LIMIT` в
    рекурсивном CTE останавливает рекурсию. [PostgreSQL](https://www.postgresql.org/docs/current/queries-with.html)
    описывает то же через рабочую таблицу, которая итерируется до пустого
    приращения. Обе реализации запрещают агрегатные функции в рекурсивной
    части. Это ограничение сохраняет монотонность, от которой зависит
    существование неподвижной точки.

### 4. NULL и порядок строк: чего запрос не обещает

Первое следствие декларативности — трёхзначная логика. Различающий пример
[SQL](../concepts/examples/index.md#sql) показывает, что `NULL = NULL` даёт
`UNKNOWN`. Здесь посмотрим, как это влияет на ответы к обычным вопросам.

```sql title="nulls_order.sql (NULL)"
--8<-- "src/sql-declarative/nulls_order.sql:nulls"
```

```text title="Вывод"
not_in_1 | dan,eve
not_managers | 0
not_managers | dan,kim,lee
```

**Проверено:** SQLite 3.51.0, macOS.

`kim` не вошла в список «не из отдела 1», хотя в отделе 1 она не работает.
Хуже со вторым вопросом. `NOT IN` по подзапросу, в котором встречается `NULL`,
не бывает `TRUE` ни для одной строки: `x NOT IN (1, 3, NULL)` раскрывается в
`x <> 1 AND x <> 3 AND x <> NULL`, а последнее слагаемое даёт `UNKNOWN`. Запрос
отвечает «руководят все», что неверно. Формулировка через `NOT EXISTS`
возвращает правильный ответ. Это поведение стандартное, а не особенность
SQLite (см. [PostgreSQL: Subquery Expressions](https://www.postgresql.org/docs/current/functions-subquery.html)).
Карточка языка относит SQL к
[`nullable_everywhere`](../languages/glossary.md#typing-nullability): `NULL`
допустим в любом типе, пока столбец не объявлен `NOT NULL`.

Второе следствие — порядок строк. Результат запроса является мультимножеством,
и порядок строк не входит в его смысл.

```sql title="nulls_order.sql (порядок)"
--8<-- "src/sql-declarative/nulls_order.sql:order"
```

```text title="Вывод"
default | ada,bob,eve,dan,lee
with_index | bob,lee,eve,dan,ada
reversed | ada,dan,eve,lee,bob
order_by | ada,bob,dan,eve,lee
```

**Проверено:** SQLite 3.51.0, macOS.

Над одними и теми же данными запрос выдал три разных порядка. Сначала строки
идут в порядке хранения, после создания индекса — в порядке обхода индекса по
`salary`. Дальше включена `PRAGMA reverse_unordered_selects`: это
отладочное расширение SQLite, которое
[переворачивает](https://www.sqlite.org/pragma.html#pragma_reverse_unordered_selects)
порядок неупорядоченных выборок, чтобы находить код, неявно полагающийся на
порядок. Детерминированный ответ получился только в последней строке, где порядок
задан явно. Синтаксис `group_concat(x, ',' ORDER BY x)` поддерживается в
SQLite начиная с 3.44.0 ([агрегатные функции](https://www.sqlite.org/lang_aggfunc.html)).
Похожие агрегаты в других СУБД называются иначе: `LISTAGG` в стандарте
SQL:2016, `string_agg` в PostgreSQL (в SQLite 3.44+ тоже есть `string_agg`).

### 5. Шов с основным языком

SQL редко используют сам по себе. Запросы встроены в программу на Python, Java
или C#. Ниже одна и та же задача решена двумя способами на одних данных:
через императивный цикл, который обращается к базе по отделу за раз, и одним
запросом.

```python title="host.py (императивно)"
--8<-- "src/sql-declarative/host.py:imperative"
```

```python title="host.py (декларативно)"
--8<-- "src/sql-declarative/host.py:declarative"
```

```python title="host.py (шов)"
--8<-- "src/sql-declarative/host.py:mismatch"
```

```text title="Вывод"
row: ('kim', None) NoneType
error: no such column: nme
imperative:  [('compilers', 3, 700), ('runtime', 2, 500)]
declarative: [('compilers', 3, 700), ('runtime', 2, 500)]
equal: True
sqlite: 3.53.4
```

**Проверено:** Python 3.14.7, модуль `sqlite3` (встроенная библиотека SQLite
3.53.4, а не CLI 3.51.0), macOS.

Результаты совпали, но устроены программы по-разному. Императивная версия
жёстко задаёт план: внешний цикл по отделам и отдельный запрос на каждый отдел.
В ORM-коде эту схему называют «N+1 запросов». Оптимизатор её не увидит,
потому что видит каждый запрос по отдельности. Декларативная версия оставляет
выбор плана СУБД.

Последний фрагмент показывает то, что называют несогласованностью
(impedance mismatch) реляционной модели и основного языка. Запрос для
Python — это строка, и опечатка в имени столбца обнаружится только при
выполнении. Результат приходит кортежами без имён. `NULL` превращается в
`None`, но трёхзначная логика при этом теряется: в Python `None == None`
истинно. Типы столбцов, ключи и мультимножественная семантика остаются по ту
сторону границы.

## Цена

**Протекающая абстракция.** Смысл запроса не зависит от индексов, а время его
выполнения зависит. В примере 1 план поменялся из-за одного `CREATE INDEX`.
На больших таблицах разница между `SCAN` и `SEARCH` — это разница между
«ответил» и «не дождались». Поэтому производительность SQL-кода оценивают по
планам, а не по тексту запроса. Программисту приходится знать, как устроен
оптимизатор, хотя декларативность обещала обратное. Кроме того, план выбирается
по статистике, и при изменении данных тот же запрос может начать работать иначе.

**Диалекты.** Стандарт ISO/IEC 9075 платный и большой, и каждая СУБД реализует
своё подмножество со своими расширениями. Только в этой статье нашлось
несколько расхождений: `EXPLAIN QUERY PLAN` против `EXPLAIN`, `group_concat`
против `string_agg`/`listagg`, динамическая типизация SQLite против
статической в стандарте (см. `typing.checking` в [карточке](../languages/sql.md)).
Перенос запросов между СУБД — отдельная работа.

**NULL.** Трёхзначная логика делает неочевидными самые простые предикаты
(пример 4). `NOT IN` и `NOT EXISTS` в учебниках часто подаются как
взаимозаменяемые, но при `NULL` они дают разные ответы. К тому же
`DISTINCT` и `GROUP BY` считают два `NULL` неразличимыми, а `=` — нет.

**Ограниченная выразительность.** Без `WITH RECURSIVE` SQL не может выразить
транзитивное замыкание, а сама рекурсия ограничена: в SQLite и PostgreSQL в
рекурсивной части нельзя использовать агрегаты, рекурсивная таблица должна
встречаться один раз, а с `UNION ALL` за завершение отвечает программист.
Задачи, которые естественно записываются циклом с изменяемым состоянием,
например симуляцию, приходится либо выносить в основной язык, либо переносить
в процедурные расширения (PL/pgSQL, SQL/PSM). Эти расширения — уже не
декларативный язык.

**Трудно отлаживать.** Нет шагов, значит, нет и места для точки останова.
Промежуточный результат можно посмотреть, только если вынести подзапрос в CTE
и выполнить его отдельно.

## Сравнение

**Datalog.** Ближайший родственник SQL. Правила `reach` из
[примера Datalog](../concepts/examples/index.md#datalog) дословно соответствуют
рекурсивному CTE (исходные правила оставлены в `reach.sql` как комментарий).
Отличий три. Отношения в Datalog — множества, поэтому ловушки `UNION ALL` там
нет. Рекурсия записывается естественно, без выделенной конструкции. Негация и
агрегаты ограничены стратификацией. SQL менее строг: мультимножества, `NULL`,
побочные эффекты `INSERT`/`UPDATE` в том же языке.

**Prolog.** Внешне похоже, но семантика другая:
[поиск цели](../languages/glossary.md#computation-rule-semantics) (goal search)
в глубину с возвратом, а не вычисление неподвижной точки. Та же программа
над графом с циклом без табулирования не завершится из-за левой рекурсии.
В SWI-Prolog нужна директива [`table`](https://www.swi-prolog.org/pldoc/man?section=tabling),
которая переводит предикат к вычислению, похожему на Datalog.

```prolog title="reach.pl"
--8<-- "src/sql-declarative/reach.pl:reach"
```

**Не запускалось:** SWI-Prolog не установлен; ожидаемые 6 решений следуют из
[документации tabling](https://www.swi-prolog.org/pldoc/man?section=tabling),
а порядок выдачи решений при табулировании не гарантирован.

**LINQ, Java Streams, методы массивов JS.** Это декларативный стиль внутри
основного языка: `filter`, `map`, группировка и свёртка вместо циклов. Шва
нет, типы проверяет компилятор основного языка (в C# и Java) или никто
(в JS). Но оптимизатора тоже нет: конвейер выполняется в записанном порядке.

```js title="streams.mjs"
--8<-- "src/sql-declarative/streams.mjs:pipeline"
```

```text title="Вывод"
[["compilers",3,700],["runtime",2,500]]
```

**Проверено:** Node.js 22.23.3, macOS.

Здесь порядок операций выбирает программист: сначала `filter`, потом
группировка. `Object.groupBy` — новый метод
([MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/groupBy)),
в Node.js 22 он есть. LINQ устроен интереснее: запрос к `IQueryable` становится
деревом выражений, которое провайдер транслирует в SQL
([LINQ](https://learn.microsoft.com/en-us/dotnet/csharp/linq/get-started/introduction-to-linq-queries)).
Это попытка закрыть шов, при которой план по-прежнему выбирает СУБД.

| | SQL | Datalog | Prolog | Streams / LINQ to Objects |
|---|---|---|---|---|
| Кратность | мультимножество, `DISTINCT` по запросу | множество | последовательность решений | последовательность |
| Рекурсия | `WITH RECURSIVE`, ограничена | естественна, завершение на конечных данных | естественна, завершение не гарантировано | через функции основного языка |
| Кто выбирает план | оптимизатор СУБД | движок (снизу вверх) | программист (порядок целей) | программист (порядок вызовов) |
| Отсутствие значения | `NULL`, трёхзначная логика | нет (факта просто нет) | нет выделенного значения | `null`/`Optional` основного языка |

## Что взять в свой язык

**Вариант 8, «Язык для работы с реляционными данными»** (см.
[варианты заданий](../labs/index.md#varianty)): встроенные типы `table`,
`row`, `column` и функции описания структур, изменения данных и поиска.
Главное проектное решение — где провести границу между декларативным и
императивным. Можно сделать поиск выражением, которое описывает результат
(`find emp where salary > 200`), а можно — функцией с явным циклом. Первый путь
даёт компилятору свободу, но обязывает определить семантику: множество или
мультимножество, есть ли порядок, что делать с отсутствующими значениями.
Запишите эти решения в описании языка до того, как писать грамматику.

**Отделите спецификацию от стратегии.** Если в языке есть декларативная
конструкция, в AST она должна быть узлом-описанием (`Select(source, predicate,
projection)`), а не заранее развёрнутым циклом. Разворачивание в цикл — задача
отдельного прохода, близкого к генерации кода. Пока узел остаётся описанием,
над ним можно делать преобразования. Это та же идея, что в
[лекции об оптимизации кода](../lectures/html/11-optimizaciya-koda.html),
только на уровне выше.

**Оптимизация запросов — это преобразование программ.** Перенос фильтра перед
соединением (predicate pushdown), перестановка соединений, замена сканирования
поиском по индексу — всё это эквивалентные переписывания дерева, корректность
которых следует из алгебры отношений. В учебном компиляторе реализуемо хотя бы
одно такое правило: `filter(p, join(a, b))` → `join(filter(p, a), b)`, если `p`
ссылается только на столбцы `a`. Перед этим семантический анализ должен знать,
каким таблицам принадлежат столбцы. Это обычная задача разрешения имён.

**Не повторяйте ошибки SQL, если можно.** Отсутствие значения лучше сделать
явным типом (`Option`), а не значением, допустимым в любом типе. Если порядок
строк не определён, скажите об этом в спецификации и добавьте в тесты режим,
аналогичный `reverse_unordered_selects`, который переставляет строки. Если есть
рекурсия, выберите множественную семантику или выдавайте диагностику о
возможном незавершении.

**Проверяйте запросы во время компиляции.** Шов из примера 5 возникает потому,
что запрос — строка. Во встроенном языке запросы — часть грамматики, и опечатку
`nme` можно найти на этапе семантического анализа по объявленной схеме таблицы.

## Упражнение

1. Предскажите вывод без запуска: что вернёт
   `SELECT count(*) FROM emp WHERE manager_id NOT IN (SELECT id FROM emp WHERE dept_id = 2);`
   на данных `data.sql`? А если заменить `dept_id = 2` на `dept_id IS NULL`?
   Проверьте в `sqlite3`.

    ??? question "Ответ"
        Подзапрос `dept_id = 2` возвращает `{3, 4}`, в нём нет `NULL`. Но у
        `ada` сам `manager_id` равен `NULL`, и `NULL NOT IN (3, 4)` даёт
        `UNKNOWN`, поэтому `ada` не считается. Остаются `bob` (1), `eve` (1),
        `lee` (2), итого `3`. Для `dept_id IS NULL` подзапрос возвращает
        `{5}` (это `kim`). Условие выполняется для `bob`, `eve`, `dan`, `kim`
        и `lee`, итого `5`; `ada` снова не считается. В обоих случаях `NULL`
        есть в проверяемом *столбце*, но не в подзапросе, поэтому ответ не
        пуст — в отличие от `not_managers` из примера 4.

2. Напишите рекурсивный CTE, который для каждого сотрудника выдаёт цепочку
   руководителей до верхнего уровня (`dan → eve → ada`). Какой оператор,
   `UNION` или `UNION ALL`, здесь безопасен и почему? Что изменится, если в
   данных появится цикл подчинения?

    ??? question "Ответ"
        Базовая часть — `SELECT id, manager_id FROM emp`, рекурсивная — соединение
        с `emp` по `manager_id`. На дереве подчинения безопасны оба оператора:
        цепочки конечны. При цикле `UNION ALL` не завершится, а `UNION` завершится
        только если строка результата не содержит растущих значений (например,
        глубины или накапливаемого пути). Со строкой-путём `a,b,a,…` каждая строка
        новая, и завершение надо обеспечивать явной проверкой
        `instr(path, …) = 0`.
