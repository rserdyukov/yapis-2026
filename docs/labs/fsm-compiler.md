# Пример компилятора: FSM → WebAssembly

Это законченный учебный компилятор, на который можно равняться в
лабораторных 2–5. Исходная задача взята из карточки «Диалог банкомата». В ней
автор эталона на Python сам придумал таблицу переходов, но проверять её было
некому. Здесь таблица превращается в язык, а компилятор **доказывает**
свойства автомата до запуска.

- Исходники лежат в [`examples/atm-lang/`](https://github.com/rserdyukov/yapis-2026/tree/main/examples/atm-lang).
- Запустить в браузере можно в [playground](../playground/index.md).
- Схемы трансляции и правила для WAT описаны в [HOWTO: генерация кода](codegen-howto.md#wat).

Язык FSM предметный, поэтому часть обязательных требований практикума
(`while`, `for`, подпрограммы с возвратом) в нём **нет**. Пример показывает
устройство конвейера и семантического анализатора, а не готовый вариант.

## Язык

```text
machine ATM

const PIN: string = "4321"
context { attempts: int = 0, balance: money = 5000 }
events  { insert_card, pin(code: string), withdraw(amount: money), cancel, timeout }

states Idle, PinWait, Menu
initial Idle
terminal Idle

action greet { say "Здравствуйте! Выберите операцию" }
action count { attempts = attempts + 1
               say "Неверный PIN. Осталось попыток: ", 3 - attempts }

Idle    -- insert_card -------------------> PinWait
PinWait -- pin(c) [c == PIN] -------------> Menu   / greet
PinWait -- pin(_) else ------------------->        / count
PinWait -- cancel | timeout --------------> Idle
Menu    -- withdraw(_) | cancel | timeout -> Idle
Idle    -- pin(_) | withdraw(_) | cancel | timeout  ignore
PinWait -- insert_card | withdraw(_)                ignore
Menu    -- insert_card | pin(_)                     ignore
```

| Конструкция | Смысл |
|---|---|
| `states`, `initial`, `terminal` | Состояния объявлены, а не «наколдованы» из строк. Опечатка даёт ошибку компиляции |
| `context { поле: тип = значение }` | Изменяемые данные автомата: `int`, `money`, `string`, `bool` |
| `events { имя(параметр: тип) }` | Алфавит автомата вместе с типами параметров |
| `action имя(параметры) { ... }` | Действие: присваивания полям, `say`, `if / else if / else` |
| `A -- e(x) [guard] -> B / act(x)` | Переход. Без цели после стрелки это переход в себя |
| `else [guard]`, `else` | Явный порядок guard'ов: этот переход проверяется, только если предыдущие не сработали |
| `A -- e1 \| e2 ignore` | Явный отказ реагировать на событие. Без него компилятор выдаст предупреждение |

### Синтаксические диаграммы

Главные правила грамматики `Fsm.g4` в виде railroad-диаграмм. Читать
слева направо: любой путь от входа до выхода — допустимая запись.
Прямоугольники со скруглением — терминалы, обычные — ссылки на другие
правила. Диаграммы нарисованы вручную по `.g4` и упрощены: метки
альтернатив и имена полей опущены.

```kroki-plantuml
@startebnf
program = "machine", ID, { decl };
decl = constDecl | contextDecl | eventsDecl | statesDecl
     | initialDecl | terminalDecl | actionDecl | transition;
@endebnf
```

Переход — самое насыщенное правило. Три альтернативы `.g4`
(`moveTransition`, `selfTransition`, `ignoreTransition`) на диаграмме
сливаются в одну развилку после триггеров. Видно, почему переход в себя
обязан иметь действие: после стрелки путь идёт либо через имя состояния,
либо сразу в `calls`.

```kroki-plantuml
@startebnf
transition = ID, DASHES, triggers,
             ( [guard], ARROW, ( ID, [calls] | calls ) | "ignore" );
triggers = trigger, { "|", trigger };
trigger = ID, [ "(", [ pattern, { ",", pattern } ], ")" ];
guard = "else", [ "[", expr, "]" ] | "[", expr, "]";
calls = "/", call, { ",", call };
@endebnf
```

## Конвейер и два фронтенда

```text
исходник ──► ANTLR 4 ─┐
                      ├─► AST ──► семантика ──► генератор ──► WAT + .wasm
исходник ──► Lark ────┘   ast.py   semantic.py   codegen.py    wasm.py
```

Грамматика написана **дважды**, разными библиотеками. Оба фронтенда строят
одно и то же AST, поэтому семантика и генератор кода у них общие. Тест
`test_frontends` сравнивает деревья через `==` на всех примерах и
негативных тестах.

| | ANTLR 4 | Lark |
|---|---|---|
| Файл | `grammar/Fsm.g4` | `fsmc/frontend_lark/fsm.lark` |
| Алгоритм | ALL(\*), нисходящий | LALR(1), восходящий |
| Парсер | генерируется Java-инструментом заранее, результат закоммичен | строится из грамматики при запуске, Java не нужна |
| Приоритеты операций | порядок альтернатив левоокурсивного `expr` | лестница правил `or_expr → and_expr → …` |
| Дерево → AST | `Visitor`: сами выбираем порядок обхода | `Transformer`: снизу вверх, метод получает готовых детей |
| Сообщения об ошибках | `ErrorListener`, текст ANTLR | исключения `UnexpectedToken` / `UnexpectedCharacters` с множеством ожидаемых терминалов |
| Размер в браузере | ~1 МБ | ~0,5 МБ |

Одна конструкция показывает, что грамматики пишут с оглядкой на алгоритм:

```antlr
// ANTLR: левая рекурсия допустима, приоритет — порядок строк
expr : expr op=('*'|'/'|'%') expr   # binExpr
     | expr op=('+'|'-') expr       # binExpr
     | INT                          # intExpr ;
```

```lark
// Lark (LALR): приоритет — вложенность правил, ?правило не создаёт узел
?add_expr: mul_expr | add_expr ADD_OP mul_expr   -> bin
?mul_expr: unary    | mul_expr MUL_OP unary      -> bin
```

Переводы строк в языке незначимы. Чтобы грамматика оставалась
однозначной (для LALR(1) это обязательно), переход в себя пишется только с
действием: `A -- e -> / act`. После стрелки идёт либо имя состояния, либо `/`.

## Семантические проверки

Номера E101–E112 совпадают со строками таблицы из карточки задачи.

| Код | Проверка | Как реализована |
|---|---|---|
| E001 / E002 | Лексическая / синтаксическая ошибка | фронтенд |
| E101 | Состояние в переходе объявлено | таблица символов, подсказка ближайшего имени |
| **E102** | Каждое состояние достижимо из начального | обход в ширину от `initial` |
| **E103** | Из каждого состояния достижимо терминальное | обход в ширину по **обращённому** графу от всех `terminal` |
| E104 | Событие объявлено | таблица символов |
| E105 | Арность и типы образца события | сравнение с объявлением |
| **E106** | Нет двух переходов по одному событию без guard'а | группировка по (состояние, событие) |
| W107 | Несколько guard'ов без явного `else` | предупреждение: порядок проверки неочевиден |
| **W108** | Каждое событие обработано в каждом состоянии или явно `ignore` | перебор (состояние × событие) |
| E109 | Действие объявлено | таблица символов |
| E110 | Имена в guard'ах и действиях существуют | области видимости: константы → поля → параметры |
| E111 | Guard имеет тип `bool` | вывод типов |
| E112 | Ровно одно начальное состояние, минимум одно терминальное | подсчёт |
| E113–E116, W117–W120 | Повторные объявления, типы, аргументы действий, образцы у `a \| b`, недостижимые переходы, неисчерпывающие guard'ы, неиспользуемые действия | см. `fsmc/semantic.py` |

Проверки E102, E103, E106 и W108 — ради них язык и существует. Это не
проверка типов, а доказательство свойств программы обходом графа, то есть
материал курса про конечные автоматы.

Главный негативный тест — `neg_10_naive.fsm`, дословный перевод
ошибочного `naive.py` из карточки. Python промолчал, а здесь сборка падает:

```text
neg_10_naive.fsm:12:9:  ошибка E112: терминальное состояние не объявлено
neg_10_naive.fsm:30:29: ошибка E102: состояние 'Dispensing' недостижимо из начального 'Idle'
neg_10_naive.fsm:56:59: ошибка E101: переход ведёт в необъявленное состояние 'Dispencing' — возможно, 'Dispensing'?
neg_10_naive.fsm:30:23: предупреждение W108: в 'Menu' не обработаны события: ..., timeout, ...
```

Четвёртая ошибка `naive.py`, `attempts > MAX` вместо `>=`, остаётся
незамеченной, и так и должно быть. Это логическая граница, её ловит
дифференциальный тест против `reference.py`, а не типы.

## Генерация кода

Модуль WebAssembly целиком выбирает компилятор. Внешний ассемблер не нужен:
`wasm.py` печатает один и тот же список инструкций в WAT и в двоичный
формат. Тест собирает наш WAT утилитой `wat2wasm` и требует, чтобы результат
побайтно совпал с нашим `.wasm`.

| Что | Как в WASM |
|---|---|
| `int`, `money`, `bool` | `i32` |
| `string` | `i32`-указатель на `[длина][байты UTF-8]` в линейной памяти, литералы в data-сегментах |
| поле контекста | `(global $ctx_balance (mut i32))` |
| текущее состояние | `(global $state (mut i32))`, номер в порядке `states` |
| действие | функция `$act_<имя>` |
| событие | экспорт `on_<имя>(параметры) -> i32`: `br_table` по `$state`, в ветке guard'ы сверху вниз |
| `and` / `or` | короткое вычисление через `if (result i32)` |
| `==` для строк | функция `$str_eq` на WAT, не импорт из JS |
| вывод | импорты `env.print_str`, `env.print_int`, `env.print_end` |
| описание машины | JSON в пользовательской секции `fsm.meta`: хост узнаёт события и типы из самого модуля |

Диспетчеризация сделана **таблицей переходов** (`br_table`), а не цепочкой
сравнений. Это одно из усложнений карточки:

```wat
(func $on_pin (param $e_code i32) (result i32)
  block $unhandled
    block $in_PinWait
      block $in_Idle
        global.get $state
        br_table $in_Idle $in_PinWait ... $unhandled
      end
      ;; Idle -- pin: ignore
      i32.const 1
      return
    end
    ;; PinWait -- pin(c) [c == PIN] -> Menu / greet
    local.get $e_code
    i32.const 404            ;; адрес литерала "4321"
    call $str_eq
    if
      call $act_greet
      i32.const 2
      global.set $state
      i32.const 0
      return
    end
    ...
```

Хост `runtime/fsm-host.mjs` один на Node и браузер. Он не знает ни одного
состояния: только передаёт события, кладёт строковые аргументы в память через
экспорт `alloc` и печатает строки.

## Запуск и тесты

```bash
cd examples/atm-lang
pip install -r requirements.txt

./compile.sh examples/atm.fsm                              # build/atm.wat, .wasm, .mmd
./compile.sh examples/atm.fsm scenarios/01_success.events  # и запуск в Node
FSMC_FRONTEND=lark ./compile.sh examples/atm.fsm           # то же через Lark
python3 -m fsmc examples/atm.fsm --emit mermaid            # диаграмма

python3 -m unittest discover -s tests -v                   # все тесты
python3 tools/gen_antlr.py                                 # после правки Fsm.g4
```

Тесты проверяют:

- равенство AST и диагностики у обоих фронтендов;
- **точный** набор кодов у каждого негативного теста (строка `// expect:`
  в самом файле), так что лишняя каскадная ошибка тоже считается регрессией;
- совпадение вывода скомпилированного WASM с `reference.py` на всех
  сценариях и с эталонным выводом из карточки;
- побайтное совпадение нашего кодировщика с `wat2wasm`;
- актуальность сгенерированного ANTLR-парсера относительно `Fsm.g4`.

## Что взять в свою работу

- **AST отдельно от дерева разбора.** Замена парсера не затронула ни
  строчки семантики и генератора. Это и есть граница между ЛР 3 и ЛР 4.
- **Коды ошибок в негативных тестах.** Тест проверяет код, а не текст
  сообщения, поэтому текст можно улучшать, не ломая тесты.
- **Дифференциальный тест против эталона.** Сценарии общие, а сравнивать
  можно вывод реализации на любом языке.
- **Один список инструкций, два принтера.** Если не хочется писать двоичный
  кодировщик, WAT + `wat2wasm` тоже засчитывается ([HOWTO, § 1](codegen-howto.md#chto-schitaetsya)).
