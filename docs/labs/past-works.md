# Решения прошлого года: что взять, чего избегать

Подборка приёмов из работ 2025 года: 22 компилятора на Python, Java, C# и
TypeScript под все пять целевых платформ. Работы названы по реализованному
языку и платформе, например «MathPL → WAT». Разделы идут в порядке
лабораторных работ.

Генерации целевого кода посвящена отдельная страница:
[HOWTO: генерация целевого кода](codegen-howto.md).

## ЛР 1. Примеры и описание языка

- **Описание каждой конструкции словами + пример + ограничения.** Лучший
  README прошлого года (MathLang → WAT) для каждой конструкции даёт
  абзац текста, пример и явный список того, что **запрещено** («неявные
  преобразования не допускаются», «объявление без инициализации запрещено»).
  Такой текст потом почти без правок идёт в раздел отчёта «Спецификация языка».
- **Обоснование решений.** В MCL → CPython есть отдельный документ «почему
  так»: почему в языке нет `null`, как ведут себя NaN и бесконечность, какие
  типы изменяемы. Это редкость. Именно такие вопросы задают на защите.
- **Примеры разложены по темам:** `examples/BaseLanguageExamples/{Cycles,
  Functions,Operations,Errors}/` (SetLang → CIL). Когда семантика или
  генератор ломаются на одной теме, сразу понятно, на какой.

## ЛР 2. Грамматика

### Приоритеты операций: левая рекурсия + метки

```antlr
expr
    : primary                                   #primaryExpr
    | <assoc=right> expr POW expr               #powExpr
    | expr op=(MUL | DIV | MOD) expr            #mulDivExpr
    | expr op=(PLUS | MINUS) expr               #addSubExpr
    | expr op=(EQ | NEQ | LT | LE | GT | GE) expr  #compExpr
    | expr AND expr                             #andExpr
    | expr OR expr                              #orExpr
    ;
```

- Приоритет задаётся **порядком альтернатив**: чем выше строка, тем сильнее
  связывает оператор.
- Метка `#label` на каждой альтернативе даёт отдельный метод
  `visitMulDivExpr`. Без меток получается один `visitExpression` на 220 строк
  с цепочкой `if ctx.MINUS() and len(ctx.children) == 1`, это тоже реальный
  пример прошлого года.
- `op=(...)` позволяет в visitor'е писать `ctx.op.type` вместо перебора
  `ctx.MUL()`, `ctx.DIV()`.
- `<assoc=right>` для возведения в степень: `2^3^2 = 2^9`.

Второй допустимый стиль — каскад правил `orExpr → andExpr → ... → primary`.
Он длиннее, но так же корректен. Хороший образец — MCL → CPython: там
тернарный оператор, лямбды и приведение `(type) expr`.

### Неявные блоки (INDENT/DEDENT)

Три подхода встретились в прошлом году:

| Подход | Оценка |
|---|---|
| Наследник сгенерированного лексера с переопределённым `nextToken()`: стек отступов, очередь отложенных токенов | **Лучший**: номера строк сохраняются, ошибки идут в общий listener |
| Постобработка готового потока токенов | Нормально, проще в отладке |
| Текстовый препроцессор, вставляющий `BEGIN`/`END` в исходник | **Не делайте**: позиции в ошибках перестают совпадать с исходным файлом |

Детали хорошей реализации (RivScript → WAT, MCL → CPython):

- виртуальные токены объявлены в грамматике через `tokens { INDENT, DEDENT }`,
  а не как `INDENT: 'indent';`, иначе появится ключевое слово `indent`;
- внутри `()`, `[]` переводы строк и отступы игнорируются;
- смешение табуляций и пробелов — ошибка;
- на EOF генерируются все недостающие DEDENT;
- ошибка отступа отправляется в штатный механизм ANTLR, поэтому попадает в
  общий список синтаксических ошибок:

```java
if (indentLength != indentStack.peek()) {
    String msg = String.format("Invalid indentation: expected %d, but got %d",
                               indentStack.peek(), indentLength);
    getErrorListenerDispatch().syntaxError(this, null,
        _tokenStartLine, _tokenStartCharPositionInLine, msg, null);
}
```

Номера токенов не прописывайте числами (`INDENT = 51`): после правки
грамматики они сдвинутся. Используйте константы сгенерированного лексера.

### Интересные расширения

- **Шаблоны (дженерики).** MathLang → WAT: `sub f:(T)(T x)`, вывод
  шаблонных аргументов из фактических параметров, явная специализация.
  Даже встроенные `read`/`cast` объявлены как шаблоны: `read:(float)()`.
  Тело шаблона проверяется при подстановке, генерация идёт по
  мономорфизации: отдельная функция `f@int`, `f@float` на каждый набор типов.
- **switch без выражения, как в Go:** `switch { case x > 0 { ... } }`.
  Удобно, если по варианту нужен многовариантный условный оператор.
- **Лямбды с параметрами-результатами и явным захватом:**
  `lambda (int input, int ?output, external a) -> { ... }`. Хорошо
  показывает связь с вариантом «передача по результату».
- **Разные виды присваивания под разными метками:** `# SingleAssign`,
  `# MultiAssign`, `# StructFieldAssign`. Генератору не нужно разбираться,
  какой это случай.

## ЛР 3. Синтаксические ошибки

### Формат сообщения

Лучший формат прошлого года (RivScript → WAT) повторяет rustc/clang:

```text
error[E201]: mismatched input ')' expecting expression
  --> examples/errors/parser/07_invalid_expression.riv:4:12
   |
 4 |     x = (1 + )
   |              ^
  hint: после '+' ожидается выражение
```

- Коды ошибок разбиты на диапазоны: E1xx лексические, E2xx синтаксические,
  E3xx семантические.
- В конце печатается итог: «N error(s) and M warning(s) generated».
- Минимально достаточно `файл:строка:колонка`, строки исходника и `^` под
  токеном. Если в строке есть табуляции, сдвигайте `^` с их учётом.

### Один listener на лексер и парсер, ошибки в список

```java
SyntaxErrorListener errors = new SyntaxErrorListener();
lexer.removeErrorListeners();  lexer.addErrorListener(errors);
parser.removeErrorListeners(); parser.addErrorListener(errors);
ParseTree tree = parser.program();
return new SyntaxAnalysisResult(tree, errors.getErrors());
```

Типичные ошибки:

- listener подключён только к парсеру, и ошибки лексера печатаются
  стандартным сообщением ANTLR;
- listener бросает исключение на первой ошибке, остальные теряются;
- listener только печатает, и `compile.sh` завершается с кодом 0 при ошибках;
- класс назван `SyntaxError` и затеняет встроенный класс Python.

**Совет, которого не было ни у кого:** последним правилом лексера поставьте
`ERROR_CHAR : . ;`. Тогда недопустимый символ становится обычным токеном,
и можно выдать понятное «недопустимый символ '№'» вместо `token recognition error`.

### Один файл — одна ошибка

```text
examples/errors/parser/05_incomplete_if.riv
# SYNTAX ERROR: if без тела
# expect: mismatched input '<EOF>'
```

Так было сделано в RivScript → WAT: 28 файлов в каталогах `lexer/`, `parser/`,
`semantic/`. Строка `expect` делает файл готовым тестом: раннер проверяет, что
компилятор выдал ошибку **с этим текстом**, а не просто «какую-то» ошибку.

## ЛР 4. Семантика

### Модульная структура

Удачный вариант раскладки (RivScript → WAT, ImgLang → CIL, Lisp → WAT):

```text
semantic/
  types.py          # типы и таблицы совместимости
  symbols.py        # Symbol, FunctionSymbol, VariableSymbol
  scope.py          # стек областей видимости
  builtins.py       # встроенные функции с сигнатурами
  analyzer.py       # обход дерева
errors/
  diagnostics.py    # классы ошибок с кодами и позициями
  reporter.py       # форматирование
```

Для Java хорошо показал себя вариант с handler'ами по видам узлов
(`FunctionHandler`, `StatementHandler`, `ExpressionHandler`) и общим
`AnalysisContext`, где лежат `ScopeManager`, список ошибок, текущая функция
и `Map<ParserRuleContext, Type> expressionTypes`. Эту карту типов потом
**переиспользует генератор кода**.

Для языков с множеством специальных форм (Lisp) обработчики хранятся в
словаре `{"lambda": LambdaHandler(), "let": LetHandler(), ...}` вместо
цепочки `if/elif`.

### Типы задаются таблицами

```python
class Compat(Enum):
    EXACT = 1; IMPLICIT = 2; EXPLICIT = 3; NONE = 4

implicit = {("int", "float")}
explicit = {("int", "float"), ("float", "int"), ("color", "pixel")}

binary_ops = {
    "+":  {("int", "int"): "int", ("float", "float"): "float",
           ("int", "float"): "float", ("string", "string"): "string"},
    "==": {("int", "int"): "bool", ...},
}
```

Правила типизации лежат **данными в одном месте**: их легко проверить и
показать в отчёте таблицей. Деление на EXACT/IMPLICIT/EXPLICIT/NONE прямо
соответствует вариантам «явное/неявное преобразование типов» (ImgLang → CIL,
GSL → LLVM с `record CastRule(Type from, Type to)`).

### Два прохода

```python
def analyze(self, program):
    self.collect_declarations(program)   # функции, структуры, сигнатуры
    self.check_bodies(program)
```

Первый проход собирает объявления, второй проверяет тела. Так работают
вызовы функции до её объявления, взаимная рекурсия и перегрузки.

### Перегрузка: лучший кандидат

```python
def find_best_match(self, arg_types):
    best, best_score, ambiguous = None, -1, False
    for cand in self.overloads:
        if len(cand.params) != len(arg_types):
            continue
        score = 0
        for p, a in zip(cand.param_types, arg_types):
            if p == a:                 score += 2
            elif implicit_ok(a, p):    score += 1
            else:                      break
        else:
            if score > best_score:     best, best_score, ambiguous = cand, score, False
            elif score == best_score:  ambiguous = True
    ...
```

Образец — XMLang: дубли сигнатур, прототипы без реализации, расхождение типа
возврата прототипа и реализации. **Чего не было ни у кого:** ошибки
неоднозначности, когда два кандидата набирают одинаковый score (в коде выше
флаг `ambiguous`). Ещё одна частая ошибка: поиск перегрузки по префиксу имени
`name__...`, который возвращает первую попавшуюся.

### Отдельный AST

Четыре работы строили собственное AST на `dataclass` / `record` вместо работы
по дереву разбора:

```python
@dataclass(kw_only=True)
class Node:
    pos: SourcePos | None = None

@dataclass(kw_only=True)
class CastExpr(Node):
    target: Type
    expr: "Expr"
```

Семантика и генератор перестают зависеть от формы грамматики, и позиция
хранится в каждом узле. Это хороший уровень для тех, кому интересно. Для
остальных достаточно visitor'а по дереву разбора с метками альтернатив.

### Диагностика с контекстом и восстановлением

Лучшая система ошибок (Lisp → WAT) даёт каждой ошибке dataclass с кодом и
диапазоном позиций, а контекст «где мы сейчас» хранит контекст-менеджером:

```python
with self.errors.context(f"функция '{name}'"):
    self.visit(body)
```

Тест `test_recovery_mode` проверяет, что анализатор находит **несколько**
ошибок подряд, а не останавливается на первой.

### Return во всех путях: слабое место всех работ

Почти везде проверка была такой: «в теле встретился хоть один `return`». Тогда
`if x { return 1 }` без `else` считается корректным. Правильный алгоритм
короткий:

```python
def returns(stmt) -> bool:
    match stmt:
        case Return():            return True
        case Block(stmts):        return any(returns(s) for s in stmts)
        case If(then, els):       return els is not None and returns(then) and returns(els)
        case _:                   return False    # циклы могут не выполниться ни разу
```

Отдельно полезно ловить **недостижимый код** после `return`/`break`: это
сделала одна работа из 22.

### Не решайте по тексту

Реальные примеры, как делать нельзя:

- `has_return = ctx.getText().startswith("return")`;
- тип возврата функции `INT`, «если в теле встречается `res`»;
- тип структуры определяется по **имени переменной**:
  `"Tuple" if name in ["t1", "p"]`;
- молчаливая перезапись символа при повторном объявлении вместо ошибки.

Все решения должны приниматься по дереву и таблице символов.

## Тесты и инфраструктура

### Тесты, которые проверяют результат

Лучший образец года — Lisp → WAT, 44 теста на `unittest`:

```python
class SemanticTest(BaseSemanticTest):
    def test_lambda_errors(self):
        _, analyzer = self.parse_and_analyze("(lambda x x)")
        assert isinstance(analyzer.errors[0], TypeMismatchError)

class CompilerTest(BaseWasmTest):
    def test_or(self):
        self.assert_evaluates("(or nil 5)", 5.0)   # компиляция + запуск + сравнение
```

Шаблон теста: **исходник, ожидаемый результат (значение, stdout или класс
ошибки) и assert**. Golden-файлов `*.expected` не было ни у кого, хотя это
самый дешёвый способ покрыть все примеры. Готовый раннер есть в
[HOWTO, § 10](codegen-howto.md#proverka).

Мелкий полезный приём: раннер подаёт программам фиксированный stdin, чтобы
тест с `read()` не зависал.

### Воспроизводимая сборка

- **Скрипт, который ставит всё сам:** venv, зависимости, нужная версия
  ANTLR-jar и wabt, генерация парсера. Работает на Windows и Unix (MathPL → WAT,
  `bootstrap_compiler.py`).
- **Maven/Gradle wrapper** (`./mvnw`, `./gradlew`) в Java-работах: сборщик
  ставить не нужно.
- **`uv` + `pyproject.toml` + `uv.lock` + `.python-version`** — самый
  воспроизводимый вариант для Python.
- **CLI на `argparse`/`click`** с флагами `-o`, `--check`, `--debug` и
  подкомандами `compile`/`run`.
- **Инструменты ищутся через `shutil.which`**, при неудаче берётся локальная
  копия, а не зашитый путь.

!!! warning "`compile.sh <файл>` — обязательное требование ЛР 3"
    В прошлом году этот скрипт не сделал **никто**. Начните с него: `set -e`,
    переход в каталог скрипта, проверка аргумента, ненулевой код возврата при
    ошибках.

### Веб-IDE

Одна работа (строковый язык → JVM) собрала на Vite + React + TypeScript IDE
с тремя вкладками: грамматика, дерево разбора, ассемблер. Ошибки
подсвечиваются в браузере, есть кнопка «скачать `.j`». ANTLR умеет
генерировать парсер на TypeScript. Отличная демонстрация на защите, но не
замена тестам и `compile.sh`.

## Частые анти-паттерны

| Проблема | Как надо |
|---|---|
| Закоммичены `*Parser.py`, `*.interp`, `*.tokens`, `antlr.jar`, `jasmin.jar`, `*.dll`, `*.exe`, `*.pyc` | `.gitignore` + скрипт генерации и загрузки |
| Зашитые пути `C:\Windows\Microsoft.NET\...`, `C:/mingw`, `/home/user/...` | `which`, переменные окружения, относительные пути |
| Скрипты только `.bat`/`.ps1` или только под `brew` | `compile.sh` + инструкция для Windows (Git Bash / WSL) |
| Файлы по 1500–2700 строк | Разделение по фазам и видам узлов |
| Эвристики по тексту исходника или сгенерированного кода | Решения по дереву, типам, таблице символов |
| Ошибки через `print`, код возврата 0 | Список ошибок, `exit 1` |
| `try/except: pass` вокруг генерации, дефолт `0`/`null` вместо ошибки | Падение с понятным сообщением «не поддерживается: …» |
| Актуальная грамматика только в отчёте, а `.g4` в репозитории старый | Один источник, отчёт ссылается на файл |
| Отчёт в `.docx`/`.pdf` | Markdown в репозитории: его видно в Pull Request |
| Экранирование Markdown испорчено (`\#`, `\*\*` по всему файлу) | Проверяйте, как отчёт отображается на GitHub |

## Коротко: десять советов

1. Сделайте `compile.sh <файл>` в первый же день ЛР 3.
2. Не коммитьте сгенерированное и бинарное.
3. Выражения пишите с левой рекурсией, метками `#label` и `op=(...)`.
4. INDENT/DEDENT делайте наследником лексера, ошибки отправляйте в listener.
5. Используйте один listener на лексер и парсер, формат `файл:строка:колонка` + `^`.
   Последнее правило лексера — `ERROR_CHAR : . ;`.
6. Типы задавайте таблицами, анализ делайте в два прохода.
7. Проверяйте return во всех путях и неоднозначность перегрузок.
8. Одна ошибка — один файл примера со строкой `expect`.
9. Тесты сравнивают вывод с `.expected`, раннер возвращает ненулевой код.
10. Генератор берёт типы из семантики и никогда не решает ничего по тексту.
