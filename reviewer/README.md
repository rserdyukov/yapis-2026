# Ревьюер лабораторных работ

Приватный репозиторий с автоматическим ИИ-ревью работ студентов.

> Этот README и всё содержимое репозитория раскатываются автоматически из
> публичного репозитория курса командой `./manage.sh sync-reviewer`.
> **Правьте не здесь, а в репозитории курса** — иначе изменения будут
> затёрты при следующей синхронизации.

## Что здесь происходит

Workflow `review` по расписанию (каждые 10 минут) обходит репозитории
студентов в организации. Он делает две независимые вещи.

**1. Назначает преподавателя ревьюером** (job `assign-reviewers`):
`reviewer/lib/assign-reviewers.sh` ставит review request на преподавателя
группы, чтобы работа попала в его очередь на GitHub. Кто какую группу
ведёт — `TEACHER_BY_GROUP` в `.github/review/config.env`.

Эта job **не зависит** от ИИ-ревью: лимиты модели не должны мешать работе
попасть к преподавателю. На плане Free для приватных репозиториев
`CODEOWNERS` не срабатывает, поэтому назначение делается через API.

**2. Проверяет PR с новыми коммитами:**

1. `reviewer/lib/discover.sh` — выбирает PR с учётом лимитов курса; размер
   PR считает **без сгенерированных файлов** (`.github/review/lib/generated-files.sh`),
   слишком большие PR помечает `oversize` для сокращённого режима;
2. `reviewer/lib/review-pr.sh` — клонирует работу, готовит diff без
   сгенерированных файлов;
3. `reviewer/lib/run-check.sh` — запускает `check.sh` лабы в контейнере
   (образ `ghcr.io/<owner>/yapis-check`) в две фазы: сначала установка
   зависимостей **с сетью, без секретов** (`install-deps.sh`: pip/maven/
   gradle/npm/dotnet по манифестам работы), затем сама проверка **без
   сети**: для ЛР2 — сборка грамматики ANTLR и прогон примеров через
   парсер, для ЛР3–5 — раскладка репозитория и `compile.sh` студента на
   примерах;
4. `opencode` читает код в режиме только-чтение (промпт — через stdin) и
   пишет ревью; в сокращённом режиме — только по результатам проверок;
5. комментарий публикуется в PR от имени GitHub App.

## Почему ревью здесь, а не в репозиториях студентов

- ключ модели не попадает к студентам (на плане Free организации
  org-секреты не привязываются к приватным репозиториям);
- минуты Actions расходуются из этого аккаунта, а не из общей квоты
  организации, которую мог бы выесть один студент;
- лимиты считаются глобально по всему курсу;
- студент не может подменить промпты и проверки в своей ветке.

## Что нужно настроить

| Тип | Имя | Назначение |
|---|---|---|
| Variable | `ORG` | организация с репозиториями студентов |
| Variable | `REPO_PREFIX` | префикс имён репозиториев (`yapis-2026-`) |
| Variable | `APP_CLIENT_ID` | Client ID GitHub App |
| Secret | `APP_PRIVATE_KEY` | приватный ключ GitHub App (`.pem` целиком) |
| Secret | `OPENROUTER_API_KEY` | ключ провайдера модели из `config.env` |

Проверить настройку: `./manage.sh doctor` в репозитории курса.

## Ручной запуск

- **Actions → review → Run workflow** — поля `only` (`<репозиторий>` или
  `<репозиторий>:<PR>`) и `dry_run`.
- Из репозитория курса: `./manage.sh review yapis-2026-ivanov:4`.

## Образ для проверок

`reviewer/Dockerfile` содержит toolchain студенческих работ (Python, JDK 21,
Node, .NET 8, ANTLR). Собирается workflow `build-check-image` еженедельно и
при изменении Dockerfile. Если студенту нужен другой инструмент — добавьте
пакет в Dockerfile в репозитории курса и запустите синхронизацию.
